# agt001 제품 로드맵 — 초기 프로토타입에서 실서비스 코드 에이전트로

> 작성일: 2026-09-25
> 결정: **실제로 쓸 수 있는 코드 에이전트 서비스**를 목표로 한다. 일정에 맞춘 타협은 하지 않고, 단계별로 완성도 있게 통합한다.
> 기존 설계 문서(`docs/hackathon/`)는 설계·조사 근거로 계속 참조한다.

## 1. 제품 정의

**한 문장:** 소상공인이 채팅(말로도 가능)으로 원하는 것을 설명하고 사진을 올리면, AI가 요구사항을 정리해 확인받은 뒤 실제로 동작하는 웹사이트를 만들어 바로 공개해 주는 서비스.

**핵심 사용자:** 펜션·카페·식당·공방 같은 소규모 사업자. 개발 지식이 없고, 휴대폰으로 주로 이용한다.

**핵심 가치 (우선순위 순):**
1. 결과물이 사용자가 말한 그대로 나온다. 요구사항 확정 → 생성 → 검증의 흐름으로 보장한다.
2. 입력이 쉽다. 모바일, 음성, 사진 업로드를 지원한다.
3. 만든 뒤에도 계속 고칠 수 있다. 대화로 부분 수정하고, 버전을 남기고, 되돌릴 수 있다.
4. 여러 사람이 함께 결정할 수 있다. 다인원 방에서 투표로 확정한다. 혼자서도 쓸 수 있다.

## 2. 설계 원칙

- **대화와 코드생성 사이에 확정 PRD를 둔다.** 코드생성은 항상 사용자가 확인한 PRD 버전만 입력으로 받는다.
- **모든 상태는 DB에 둔다.** 인메모리 dict와 JSON 파일은 단계적으로 없앤다.
- **각 단계는 그 자체로 완결된다.** 단계가 끝날 때마다 테스트 통과, 로컬 검증, 스테이징 검증, 운영 배포가 끝난 상태여야 다음 단계로 넘어간다.
- **보안은 타협하지 않는다.** OAuth state 검증, 쿠키 속성, 업로드 검증, 샌드박스 격리, 비밀키 관리.
- **추측하지 않고 실측한다.** 초기 개발 기간에 발견한 버그 대부분이 실측으로 드러났다. 이 문화를 유지한다.

## 3. 단계별 통합 계획

각 단계는 **설계 문서 → 구현 → 자동 테스트 → 로컬 검증 → 스테이징 배포·검증 → 운영 배포** 순서로 진행한다.

### 0단계. 기반 정비 (다른 모든 단계의 전제)

지금 구조는 초기 프로토타입용이라 실서비스를 그 위에 쌓으면 나중에 갈아엎게 된다. 그래서 가장 먼저 한다.

| 항목 | 내용 |
|---|---|
| 코드 구조 | `backend.py`(834줄 단일 파일)를 패키지로 분리한다: `app/api`, `app/services`(chat, prd, codegen, deploy), `app/db`, `app/auth` |
| 웹서버 | Flask 개발 서버를 gunicorn(프로덕션 WSGI)으로 교체 |
| DB | PostgreSQL 16 컨테이너 + Alembic 마이그레이션. 세션·방·메시지를 전부 DB로 이전 |
| 작업 큐 | 코드생성을 스레드에서 작업 큐(Redis + RQ)로 이전. 재시작해도 작업이 사라지지 않고, 동시 실행 수를 제한할 수 있다 |
| 테스트 | pytest 단위·통합 테스트, Playwright E2E(입장→대화→생성→배포) |
| CI | GitHub Actions로 테스트·린트 자동 실행 |
| 환경 분리 | 로컬 / 스테이징 / 운영 compose 분리. 스테이징은 같은 OCI 인스턴스의 별도 포트 |
| 배포 | `deploy.sh`에 배포 전 스냅샷과 `rollback.sh` 추가 (`DEPLOYMENT_STRATEGY.md` 권고) |
| 관측 | 구조화 로그, 에러 추적, NIM 호출량·비용 기록 |

**완료 기준:** 기존 기능(1:1 채팅, 공유방, 시안, 코드생성, 배포)이 새 구조에서 전부 동작하고 E2E 테스트가 통과한다. 사용자 입장에서 보이는 변화는 없다.

### 1단계. 계정과 랜딩

| 항목 | 내용 |
|---|---|
| 랜딩 페이지 | 가치 제안, 예시 결과물, 시작하기 버튼, 카카오·구글 로그인 |
| 로그인 | 카카오 OAuth + 구글 OAuth. 비밀번호는 저장하지 않는다 |
| 세션 | 서버 세션 쿠키 (HttpOnly, Secure, SameSite=Lax) |
| 게스트 흐름 | 로그인 없이 시작 가능. 로그인하면 게스트 때 만든 방이 계정으로 옮겨진다 |
| 내 프로젝트 | 로그인 사용자의 방·프로젝트 목록 |
| 카카오톡 ID | 선택 정보. 채팅방 안에서 필요할 때 연결 |

**완료 기준:** 두 방식으로 로그인하고, 게스트 방이 계정으로 귀속되고, 다른 사용자의 방에는 접근할 수 없다.
**상세 계획:** `docs/hackathon/LANDING_AUTH_DB_UPLOAD_PLAN.md`

### 2단계. PRD 엔진 (품질의 핵심)

| 항목 | 내용 |
|---|---|
| PRD 스키마 | 업종·목적, 타깃, 섹션 구성, 섹션별 내용, 디자인 톤, 필수 정보(연락처·주소·영업시간), 이미지와 용도, 금지 사항, 완료 기준 |
| 자동 채우기 | 사용자가 순서 없이 말해도 AI가 알맞은 칸에 분류 |
| 빈 칸 질문 | 가장 중요한 빈 칸 하나만 선택지와 함께 질문 |
| PRD 카드 | 채팅방 옆(모바일은 탭)에 항상 표시. 채워진 칸과 빈 칸 구분 |
| 확정과 버전 | 생성 직전 전체 요약을 보여 주고 확정. 다인원 방은 과반 투표. 확정본은 v1, v2… 로 고정 |
| 기본값 모드 | "알아서 해줘"면 기본값으로 채우되 카드에 기본값으로 표시 |
| 실시간 | 폴링을 SSE로 교체해 AI 응답 스트리밍과 카드 갱신을 즉시 반영 |

**완료 기준:** 대화만으로 PRD의 필수 칸이 모두 채워지고, 사용자가 카드에서 내용을 확인한 뒤 확정할 수 있다.
**근거 문서:** `docs/hackathon/PRD_REQUIREMENTS_ELICITATION.md`, `REQUIREMENTS_ELICITATION_UX_REACT_REVIEW.md`

### 3단계. 코드생성 품질

| 항목 | 내용 |
|---|---|
| 입력 | 대화 원문이 아니라 확정 PRD만 Hermes에 전달. 800자 제한 제거, PRD 크기 상한 적용 |
| 산출물 | 단일 HTML에서 여러 파일 구조로 확장(HTML/CSS/JS + assets). 반응형·접근성 기본 적용 |
| 자동 검증 | PRD 완료 기준 체크(섹션 존재, 필수 문구, 이미지 참조), HTML 검사, Playwright 스크린샷, 모바일 렌더링 확인 |
| 자동 보정 | 검증 실패 시 사용자에게 보이기 전에 1회 재생성 |
| 미리보기 | 생성 결과를 채팅방 안 iframe으로 바로 확인 |
| 부분 수정 | "객실 사진을 더 크게" 같은 요청은 전체 재생성이 아니라 해당 부분만 수정 |
| 버전 | 생성본마다 스냅샷. 이전 버전 비교·복원 |

**완료 기준:** 확정 PRD의 완료 기준을 자동 검증이 통과한 결과만 사용자에게 보여진다. 수정 요청이 반영된 새 버전을 이전 버전과 나란히 볼 수 있다.

### 4단계. 사진과 음성 입력

| 항목 | 내용 |
|---|---|
| 사진 업로드 | 파일 선택·붙여넣기·끌어놓기·모바일 카메라. jpeg/png/webp만 허용, 매직바이트 검증, 크기 제한 |
| 개인정보 | EXIF 위치정보 자동 제거 (펜션 사진 GPS 노출 방지) |
| 처리 | 썸네일 생성, 채팅에 이미지 메시지로 표시, 용도(메인 배너, 객실 등)를 PRD에 연결 |
| 코드생성 연동 | 확정 PRD의 이미지를 산출물 `assets/`로 복사하고 프롬프트에 파일명·용도 목록 전달 |
| 저장소 | 초기에는 파일시스템 볼륨. 용량이 커지면 OCI Object Storage(Always Free 20GB)로 이전 |
| 음성 입력(STT) | 1차: 브라우저 내장 음성인식(Web Speech API, HTTPS 필요 — 적용 완료). 2차: 지원 안 되는 기기용 서버 음성인식 |
| 음성 출력(TTS) | 선택 기능. AI 답변 읽어주기 버튼 |

**완료 기준:** 휴대폰에서 말과 사진만으로 PRD를 채우고, 올린 사진이 실제 결과 페이지에 쓰인다.

### 5단계. 공개와 전달

| 항목 | 내용 |
|---|---|
| 프로젝트별 주소 | `프로젝트명.도메인`으로 공개. 와일드카드 인증서가 필요해 **직접 구매한 도메인이 필요**하다 |
| 게시 모델 | 생성본을 바로 공개하지 않고 "게시" 버튼으로 공개. 게시 후 수정은 다시 게시할 때만 반영 (Lovable 방식) |
| 사람 최종 검토 | 게시 전 검토 게이트 (`REVIEW_GATE_DESIGN.md`) |
| 공유 | 카카오톡 공유, QR 코드 |
| 사용자 도메인 | 선택 기능. 사업자 소유 도메인 연결 |
| 내보내기 | 소스 zip 다운로드 |

**완료 기준:** 사용자가 게시한 사이트가 고유 주소로 공개되고, 게시 이력을 보고 되돌릴 수 있다.

### 6단계. 운영과 확장

| 항목 | 내용 |
|---|---|
| 샌드박스 제한 | 코드생성 컨테이너 메모리·CPU·시간 제한, 동시 실행 수 제한, 타임아웃 시 컨테이너 정리 |
| 남용 방지 | 요청·업로드·생성 횟수 제한 |
| 비용 관리 | 사용자별 NIM 호출량 집계, 한도 초과 알림, 월 예산 가드 |
| 백업 | PostgreSQL 일일 백업, 업로드 파일 백업, 복구 훈련 |
| 모니터링 | 헬스체크, 가동 알림, 에러율 |
| 보안 점검 | 단계별 보안 리뷰, 의존성 취약점 점검 |

실제 단가 기반 견적, 결제, 관리자 대시보드, 사용 분석, 요금제.
