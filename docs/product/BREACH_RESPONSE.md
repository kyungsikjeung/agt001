> **법률 자문 아님.** 기한·신고 기준은 법률 검토(P2-1, PRIVACY_NOTES L1~L6) 때 확인받는다.

## 0. 무엇이 "유출"인가

| 등급 | 예 | 할 일 |
|---|---|---|
| **A. 열쇠 유출** | 서버 SSH 키, `.env`, API 키(NVIDIA·Gemini·Solapi·포트원·카카오 시크릿), `TOKEN_ENC_KEY`, DB 비밀번호가 남의 손에 갔을 수 있음 | §1 → §2 |
| **B. 개인정보 유출** | 사장님·손님 연락처, 문의·예약·주문, 채팅 원문이 밖으로 나감(또는 A로 서버에 누가 들어왔음) | §1 → §2 → §3 |

열쇠 유출(A)은 서버 기록에서 침입 흔적이 **없다고 확인되기 전까지** B로 다룬다.

## 1. 처음 1시간: 막기

1. **새 열쇠 먼저, 옛 열쇠 폐기.** 서버 SSH 키 교체(`~/.ssh/authorized_keys`에서 옛 공개키 삭제), 감염된 기기에 있던 API 키 전부 재발급. 키는 `/admin` 키 탭이나 서버 `.env`에서 바꾼다(ADMIN_CONTRACT §3).
2. 감염 기기는 키 교체에 쓰지 않는다(새 키를 또 빼앗긴다). 다른 기기나 OCI 콘솔의 Cloud Shell에서 한다.
3. 의심 사이트·계정은 `/admin` → 가게 → "사이트 내리기"(ADMIN_CONTRACT §3-2).
4. 시각을 적어 둔다: 알게 된 때, 막은 때. 신고 기한은 **알게 된 때**부터 센다.

## 2. 그날 안: 범위 확인

| 확인 | 어디서 |
|---|---|
| 누가 서버에 들어왔나 | 서버 `last`, `/var/log/auth.log`(SSH 로그인 성공 IP), OCI 콘솔 감사 로그 |
| DB를 뺐나 | 서버의 낯선 `pg_dump`·큰 바깥 전송, `docker logs` |
| 관리자 화면에서 뭘 봤나 | `admin_audit` 테이블(관리자가 본 것·바꾼 것) |
| 키로 돈을 썼나 | NVIDIA·Gemini·Solapi·포트원 콘솔 사용량 |
| 몇 명의 무엇이 | 유출 시점 기준 `users`·`inquiries`·`bookings`·`orders`·`customers` 행 수 |

백업으로 되살려야 하면 운영에 바로 복원하지 말고 `scripts/restore_drill.sh`로 먼저 확인한다(DB_OPERATIONS §7).

## 3. 개인정보가 나갔으면: 알리기 (개인정보 보호법 제34조, **기한·기준 확인 필요**)

| 누구에게 | 언제 | 무엇을 |
|---|---|---|
| 정보주체(사장님·손님) | 알게 된 때부터 **72시간 안**(확인 필요) | 나간 항목, 때와 경위, 피해를 줄이는 방법(예: 낯선 전화 주의), 우리가 한 조치, 문의 창구 |
| 개인정보보호위원회 또는 KISA(118, privacy.go.kr) | 72시간 안(확인 필요). 1천 명 이상, 민감·고유식별정보, **외부 침입(해킹)으로 인한 유출**이면 신고 대상으로 알려져 있음 | 위와 같음 + 유출 규모 |
| 손님 정보를 맡긴 가게 사장님 | 위와 함께 | 그 가게 손님 정보가 나갔는지. 가게가 개인정보처리자인지 우리가 수탁자인지는 L-항목에서 정리 |

연락 수단: 사장님은 카카오 "나에게 보내기"·문자(Solapi), 손님은 문의·예약에 남긴 연락처. 사이트 첫 화면 공지도 함께.
