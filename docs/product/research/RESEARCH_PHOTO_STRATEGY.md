# 사진 전략 연구: 음식점인데 사진이 없는 문제

> 작성 날짜: 2026-09-26 / 마감: 2026-09-28 / 쓰는 말: 쉬운 한국어

## 5줄 요약

1. 지금은 사진 칸이 필수 칸에 없어서, 사진을 안 올려도 질문이 끝나고 예시 그림으로 사이트가 나온다.
2. 사진 요청은 대화가 끝날 때 한 번만 나오고, 웹에서 가게 정보를 가져오는 기능은 일부러 빼둔 상태이다.
3. 남의 가게 사진이나 검색 사진을 함부로 쓰면 저작권과 약관 위반이 되고, 음식 사진은 손님을 속인 광고가 될 수 있다.
4. 무료 사진이나 AI 그림도 실제 가게 사진처럼 보이면 위험하므로, 꼭 "예시"라고 표시해야 한다.
5. 마감 전에는 사진 요청을 맨 앞으로 당기고 예시 표시를 분명히 하고, 마감 뒤에 사장님 확인 뒤에만 외부 사진을 쓰는 흐름을 추천한다.

## 1. 왜 사진이 빠지는지: 코드를 읽고 확인한 사실

### 1.1. 업종별 필수 칸에 사진이 없다

- 요구사항 칸은 모두 14개이다. 업종, 가게 이름, 사이트 목적, 대상 손님, 상품·메뉴, 담을 내용, 필요한 기능, 뺄 것, 연락 방법, 전화번호, 영업시간, 위치, 가격, 특징이다. 사진 칸은 없다. (출처: app/services/prd_schema.py 30-45 / 확인 날짜: 2026-09-26)
- 사실로 지어내면 안 되는 칸은 전화번호, 영업시간, 위치, 가격 4개뿐이다. (출처: app/services/prd_schema.py 47 / 확인 날짜: 2026-09-26)
- 식당 필수 칸은 업종, 가게 이름, 메뉴, 영업시간, 연락 방법, 사이트 목적 6개이다. 사진이 없다. (출처: app/services/prd_schema.py 107-113 / 확인 날짜: 2026-09-26)
- 카페, 펜션, 미용실, 공방, 학원 필수 칸에도 사진이 없다. (출처: app/services/prd_schema.py 86-144 / 확인 날짜: 2026-09-26)
- 다음에 물을 것을 정하는 함수는 필수 칸과 숨은 항목만 본다. 사진을 묻는 부분이 없다. (출처: app/services/prd_engine.py 538-573 / 확인 날짜: 2026-09-26)
- 질문이 끝나면 남은 필수 칸을 가정이나 자리 표시로 채운다. 사진은 대상이 아니다. (출처: app/services/prd_engine.py 576-596 / 확인 날짜: 2026-09-26)
- 같은 칸을 3번 물어도 못 채우면 가정이나 자리 표시로 넘어간다. 사진은 이 규칙과 관계가 없다. (출처: app/services/prd_engine.py 60-62, 610-616 / 확인 날짜: 2026-09-26)
- 입구에서 금지 요청을 거르는 기능은 사칭, 피싱 같은 위험 요청만 본다. 사진이나 웹 검색과 관계가 없다. (출처: app/services/intake.py 42-48 / 확인 날짜: 2026-09-26)

### 1.2. 사진 요청은 맨 마지막에 한 번뿐이다

- 사진 요청 문구는 하나로 정해져 있다. "가게 사진이 있으면 사진 버튼으로 올려 주세요. 없으면 업종에 맞는 예시 그림으로 만들고, 나중에 올리셔도 바로 바뀌어요."라는 내용이다. (출처: app/services/chat_flow.py 105 / 확인 날짜: 2026-09-26)
- 이 문구는 질문이 다 끝나고 요약할 때 붙는다. 공유방이고 아직 올린 사진이 없을 때만 나온다. 일대일 채팅에서는 안 나온다. (출처: app/services/chat_flow.py 269-283 / 확인 날짜: 2026-09-26)
- 시안을 만든 뒤에도 같은 조건일 때 한 번 더 나온다. "지금은 사진 대신 예시 그림이 들어가 있어요. 사진 버튼으로 올리면 시안에 바로 넣어 드려요."라는 내용이다. (출처: app/services/chat_flow.py 343-344 / 확인 날짜: 2026-09-26)
- 결과적으로 식당 사장님이 대화 초반에 사진을 안 올리면, 끝까지 사진 이야기가 안 나올 수 있다. 사진 없이도 질문 예산 8개가 끝나면 요약과 시안으로 넘어간다. (출처: app/services/prd_schema.py 16, app/services/chat_flow.py 269-283 / 확인 날짜: 2026-09-26)

### 1.3. 사진 올리기는 되지만 필수가 아니다

- 올릴 수 있는 사진은 JPEG, PNG, WebP뿐이다. 10MB까지, 한 방에 30장까지이다. (출처: app/services/photos.py 17-20, 38-47, 68-69 / 확인 날짜: 2026-09-26)
- 올린 사진은 위치 정보를 지우고 긴 쪽을 1600픽셀로 줄여서 JPEG로 다시 저장한다. 원본은 보관하지 않는다. (출처: app/services/photos.py 35-53 / 확인 날짜: 2026-09-26)
- 올린 사진은 요구사항 카드의 사진 목록에 들어가고, 시안과 공개 사이트의 대표 사진과 사진첩에 쓰인다. (출처: app/services/photos.py 76-85 / 확인 날짜: 2026-09-26)
- 시안이 이미 있으면 사진을 넣어 3안을 다시 만들고, 공개했으면 공개본도 바꾼 뒤 방에 알린다. (출처: app/services/photos.py 115-134 / 확인 날짜: 2026-09-26)
- 하지만 사진을 안 올려도 막히지 않는다. 사진이 필수가 아니므로 빈 채로 다음 단계로 간다. (출처: app/services/photos.py 56-85, app/services/chat_flow.py 280 / 확인 날짜: 2026-09-26)

### 1.4. 웹 검색과 외부 조사는 일부러 빼두었다

- 코드 어디에도 웹 검색으로 가게 이름, 주소, 사진을 가져오는 부분이 없다. intake, prd_engine, chat_flow, photos, design_variants, site_render 모두 외부 검색 호출이 없다. (출처: 위 파일 전체를 읽음 / 확인 날짜: 2026-09-26) (확인 못 함: 파일 바깥에 숨은 호출이 있는지까지는 다 보지 못함)
- 결정 문서에 분명히 적혀 있다. "웹 검색으로 가게 사실을 채우지 않는다. 조사 에이전트는 대화 밖에서 사례집 후보를 모으고 사람이 승인할 때만 쓴다." (출처: docs/product/DECISIONS.md D34 / 확인 날짜: 2026-09-26)
- 템플릿으로 시작할 때도 "업종과 구성만 가정으로 채우고, 가게 사실은 비운다."라고 정했다. 남의 정보나 예시 가게 정보를 실제 사이트에 넣지 않기 위해서이다. (출처: docs/product/DECISIONS.md D26 / 확인 날짜: 2026-09-26)
- 모르는 사실은 자리 표시로 두고 공개 전에 채우거나 빼게 한다. (출처: docs/product/DECISIONS.md D23 / 확인 날짜: 2026-09-26)
- 남은 할 일 목록에 "대화 밖 조사 에이전트"가 있고 베타 뒤로 미뤄져 있다. (출처: docs/product/BACKLOG.md Q-11, STATUS.md 81 / 확인 날짜: 2026-09-26)
- 문의 분류 게이트 설계에도 웹 검색으로 사실을 채우는 흐름이 없다. 질문 예산은 가게 8개, 개인 7개, 단체 8개, 웹서비스 12개이다. (출처: docs/product/INTAKE_GATE_DESIGN.md 6장 / 확인 날짜: 2026-09-26)

### 1.5. 사진 없이 끝까지 가면 화면이 이렇게 된다

- 식당 출발 샘플은 대표 사진이 비어 있고, 사진첩도 비어 있다. (출처: templates/samples/restaurant.json 1 / 확인 날짜: 2026-09-26)
- 시안 명세는 올린 사진이 있을 때만 대표 사진과 사진첩을 채운다. 사진이 없으면 빈 채로 둔다. (출처: app/services/design_variants.py 94, 103-115 / 확인 날짜: 2026-09-26)
- 간결형 3안은 사장님 사진이 없으면 사진첩을 뺀다. 사진 강조형 2안은 사진첩을 첫 화면 바로 뒤로 옮긴다. 사진이 없어도 구성만 바뀌고 사진 요청은 따로 없다. (출처: app/services/design_variants.py 182-197 / 확인 날짜: 2026-09-26)
- 렌더 단계에서 대표 사진이 비면 업종별 예시 그림 SVG를 넣고 "예시 이미지" 표시를 붙인다. (출처: app/services/site_render.py 79-83, 713-718 / 확인 날짜: 2026-09-26)
- 사진이 0장인 사진첩도 예시 그림 2장과 "사장님 사진으로 바뀌어요" 안내를 넣는다. (출처: app/services/site_render.py 86-103 / 확인 날짜: 2026-09-26)
- 시안에서는 예시 표시가 보인다. 하지만 공개 사이트에서는 예시 표시를 숨긴다. (출처: app/services/site_render.py 739-740, templates/site.css 712 / 확인 날짜: 2026-09-26)
- 결과적으로 식당 사장님이 사진을 안 올리면, 시안에는 예시 그림이 나오고 공개본에서는 예시라는 표시 없이 그림이 나올 수 있다. 손님은 실제 가게 사진으로 오해할 수 있다. (출처: 위 두 파일로 추론 / 확인 날짜: 2026-09-26)

### 2.2. (a) 대화 초반에 업종별로 사진을 강하게 요청

- 내용: 식당, 카페, 펜션은 사진을 필수처럼 묻는다. 대화 시작이나 가게 이름을 말한 뒤 바로 "대표 사진 1장과 메뉴 사진 2장을 올려 주세요"라고 한다. 휴대폰 카메라로 바로 찍도록 안내한다.
- 좋은 점: 실제 사진이라 품질이 가장 좋다. 법적 위험이 적다. 원칙과도 맞는다.
- 어려운 점: 사장님이 바쁘면 사진을 안 올릴 수 있다. 이때 대안이 없으면 다시 예시 그림 문제로 돌아간다. 대화가 길어지면 중간에 그만둘 수 있다. (출처: 확인 못 함. 우리 서비스의 이탈 수치로 확인 필요)
- 마감 전 가능 여부: 가능. 질문 순서와 문구, 사진 버튼 안내만 바꾸면 된다. 파일 수정이 적다. (출처: app/services/prd_engine.py 538-573, app/services/chat_flow.py 105의 구조로 판단 / 확인 날짜: 2026-09-26)
- 휴대폰 카메라 바로 찍기 유도는 지금 사진 올리기 기능과 잘 맞는다. 사진은 위치 정보를 지우고 줄여서 저장하므로 개인정보 노출이 적다. (출처: app/services/photos.py 35-53 / 확인 날짜: 2026-09-26)

### 2.3. (b) 가게 이름과 지역으로 웹 검색해 가져오기

#### 네이버 플레이스와 네이버 검색 API

- 네이버 지역 검색 API는 업체와 상호 검색 결과를 준다. 위치 기반 검색은 지원하지 않는다고 적혀 있다. (출처: https://github.com/naver/naver-openapi-guide/blob/master/ko/naver-openapi-swagger.yaml / 확인 날짜: 2026-09-26)
- 네이버 이미지 검색 API는 검색어에 맞는 이미지 주소와 미리보기 주소를 준다. 하루 호출 한도는 25,000회라고 적혀 있다. (출처: https://developers.naver.com/docs/serviceapi/search/image/image.md / 확인 날짜: 2026-09-26)
- 하지만 결과 사진의 저작권은 네이버나 원래 만든 사람에게 있다. API 이용 승낙이 권리를 넘긴다는 뜻이 아니라고 약관에 적혀 있다. (출처: https://developers.naver.com/products/terms/ / 확인 날짜: 2026-09-26)
- 검색 결과는 따로 떼어 보여주고, 앞뒤나 중간에 다른 내용을 넣거나 순서를 바꾸면 안 된다. 출처를 보여주고 원래 글로 가는 링크를 줘야 한다. 2026-09-07부터 바뀐 약관에 적혀 있다. (출처: https://developers.naver.com/notice/article/33400 / 확인 날짜: 2026-09-26)
- 검색 결과를 복사, 저장, 캐시하거나 다른 사람에게 주거나 팔 수 없다. AI에 넣거나 학습에 쓰는 것도 금지이다. 검색 결과가 보이는 페이지에 광고를 붙이거나 돈벌이에 쓰는 것도 금지이다. (출처: https://developers.naver.com/notice/article/33400 / 확인 날짜: 2026-09-26)
- 잠시 보관은 기기는 24시간이나 새 검색 전까지, 서버는 이력 조회로 최대 21일까지만 된다. 시간이 지나면 바로 지워야 한다. (출처: https://developers.naver.com/notice/article/33400 / 확인 날짜: 2026-09-26)
- 결론: 네이버 사진을 사이트 대표 사진처럼 저장해서 쓰는 것은 약관 위반이 될 수 있다. 검색 결과를 보여주는 용도가 아니라 사이트 재료로 쓰는 것은 목적에 맞지 않는다. (출처: 위 약관으로 판단 / 확인 날짜: 2026-09-26)
- 네이버 검색 API는 NAVER API HUB로 옮기는 중이다. 2026-07-31 뒤에는 새로 신청이 막히고, 기존 이용은 2027-06-30까지만 된다. (출처: https://developers.naver.com/notice/article/32530 / 확인 날짜: 2026-09-26)
- HUB 뒤의 정확한 사진 관련 비용은 확인 못 함이라고 쓴다. 무료 쿼터 뒤 종량제를 한다고만 나와 있다. (출처: https://developers.naver.com/notice/article/32530 / 확인 날짜: 2026-09-26) (확인 못 함: 사진 1장당 얼마인지)

- 결론: 비공식 긁기는 쓰지 않는 것이 좋다.

#### 구글 지도 Places API

- 구글 Place Photos는 Places 데이터베이스의 수백만 장 사진을 쓸 수 있게 해준다. Place Details, Nearby Search, Text Search에서 사진 이름을 받은 뒤 사진을 요청한다. (출처: https://developers.google.com/maps/documentation/places/web-service/place-photos / 확인 날짜: 2026-09-26)

- "이 가게 맞나요?" 확인 흐름이 꼭 필요하다. 같은 이름 가게가 많고 사진도 남이 올린 것이라 틀릴 수 있다. 확인 없이 쓰면 원칙 위반이다. (출처: 확인 못 함. 구글 문서에 확인 흐름이 정해져 있지 않음)

#### 인스타그램

- 인스타그램 oEmbed로 글의 넣기 코드를 받아 사이트에 넣을 수 있다. 사진, 동영상, 릴스를 블로그나 사이트에 넣는 용도이다. (출처: https://developers.facebook.com/docs/instagram-platform/oembed / 확인 날짜: 2026-09-26)

- 넣은 글은 쓴 사람 이름과 링크가 같이 보여서 출처 표시가 된다. (출처: https://developers.facebook.com/docs/instagram-platform/embed-button/ / 확인 날짜: 2026-09-26)
- 남의 사진을 빼서 대표 사진처럼 쓰는 것은 안 된다. 사업자 로그인과 허락이 있으면 본인 사진에 접근할 수 있다. 긴 토큰은 60일마다 새로 고쳐야 한다. (출처: https://developers.facebook.com/docs/instagram-platform/instagram-api-with-instagram-login/business-login/ / 확인 날짜: 2026-09-26)

#### (b) 정리

- 품질: 위치와 전화번호 확인에는 좋지만, 사진은 출처가 불분명하고 최신이 아닐 수 있다.
- 법적 위험: 높음. 네이버는 저장과 재사용 금지, 구글은 표시 의무, 인스타그램은 넣기만 허용이다.
- 비용: 카카오 소량은 싸고, 구글은 건당 비싸다. 네이버 HUB 뒤 비용은 확인 못 함.
- 구현 난이도: 어려움. 가게 찾기, 동명이인 처리, 사장님 확인, 출처 표시, 삭제 요청 대응이 필요하다.
- 원칙 충돌: 큼. 사장님이 말하지 않은 사실을 가져오므로 D26과 D34에 걸린다.
- 마감 전 가능 여부: 어려움. 읽기만 하는 확인 도움까지도 마감 전에는 무리이다.

### 2.4. (c) 무료 상업용 스톡 사진

#### Unsplash

- Unsplash 사진은 상업용과 개인용 대부분에 무료로 쓸 수 있다. 허락을 받거나 이름을 밝히지 않아도 된다고 적혀 있다. (출처: https://help.unsplash.com/en/articles/2612315-can-i-use-unsplash-images-for-personal-or-commercial-projects / 확인 날짜: 2026-09-26)
- 사진을 모아 비슷한 서비스를 만들 권리는 주지 않는다. (출처: https://unsplash.com/terms / 확인 날짜: 2026-09-26)
- API로 쓰면 규칙을 지켜야 한다. 사진가와 Unsplash 표시를 제대로 해야 한다. (출처: https://unsplash.com/documentation/ / 확인 날짜: 2026-09-26)
- 데모는 시간당 50회, 승인 뒤 생산용은 시간당 1,000회 제한이다. 사진 주소는 API가 준 주소를 그대로 써야 하고, 쓰는 시점에 다운로드 주소를 호출해야 한다. (출처: https://unsplash.com/documentation/ , https://unsplash.com/documentation/changelog / 확인 날짜: 2026-09-26)
- API로 팔지 않은 사진을 직접 팔거나 제품에 그대로 붙이는 것은 안 된다. (출처: https://help.unsplash.com/en/articles/2511245-unsplash-api-guidelines / 확인 날짜: 2026-09-26)

#### Pexels

- Pexels 사진과 동영상은 무료로 내려받아 쓸 수 있다. 이름을 밝히지 않아도 되지만 밝혀주면 좋다고 적혀 있다. (출처: https://www.pexels.com/license/ / 확인 날짜: 2026-09-26)
- 사이트, 쇼핑몰, 뉴스레터, 책, 발표, 파는 템플릿에도 쓸 수 있다. (출처: https://www.pexels.com/license/ / 확인 날짜: 2026-09-26)
- 그대로 복사해 포스터나 제품으로 팔거나, 다른 스톡 사이트에 다시 올리면 안 된다. (출처: https://www.pexels.com/license/ / 확인 날짜: 2026-09-26)
- API는 무료이다. 기본은 시간당 200회, 한 달 20,000회이다. 표시를 잘 하면 무제한으로 늘려준다고 적혀 있다. (출처: https://www.pexels.com/api/documentation / 확인 날짜: 2026-09-26)
- API로 쓸 때는 Pexels 링크나 로고를 보여줘야 한다. 사진가 이름도 가능하면 밝혀야 한다. (출처: https://www.pexels.com/api/ , https://www.pexels.com/api/documentation / 확인 날짜: 2026-09-26)

#### Pixabay

- Pixabay는 무료로 쓰고 바꿔 쓸 수 있다. 이름을 밝히지 않아도 된다. (출처: https://pixabay.com/service/license-summary/ / 확인 날짜: 2026-09-26)
- 그대로 팔거나 나눠주면 안 된다. 상표가 보이는 사진은 상품용으로 쓸 수 없다. 사람 사진은 나쁘거나 법에 어긋나게 쓰면 안 된다. 속이거나 오해하게 쓰면 안 된다. 상표나 상호로 쓰면 안 된다. (출처: https://pixabay.com/service/license-summary/ / 확인 날짜: 2026-09-26)
- 이 "속이거나 오해하게 쓰면 안 된다"는 부분이 식당에 중요하다. 남의 음식 사진을 우리 메뉴처럼 쓰면 약관 위반이 될 수 있다.
- API로 쓰면 검색 결과가 보일 때 출처를 보여줘야 한다. (출처: https://pixabay.com/api/docs/ / 확인 날짜: 2026-09-26)

#### 스톡 사진의 오해 위험과 표시 방법

- 스톡 음식을 실제 메뉴처럼 쓰면 손님이 속을 수 있다. Pixabay도 오해하게 쓰지 말라고 정했다. (출처: https://pixabay.com/service/license-summary/ / 확인 날짜: 2026-09-26)
- 그러므로 스톡을 쓰면 "예시 사진", "실제 메뉴와 다를 수 있음", 사진가 이름을 꼭 붙여야 한다. 대표 사진과 메뉴 사진에는 쓰지 않고 배경이나 분위기 사진에만 쓰는 것이 안전하다.
- 품질: 그럴듯하지만 실제 가게가 아니라서 신뢰가 떨어진다.
- 법적 위험: 표시 없이 실제처럼 쓰면 중간에서 높음. 표시하면 낮아짐.
- 비용: 무료이나 호출 제한과 표시 의무가 있다.
- 구현 난이도: 쉬움.
- 원칙 충돌: 중간. 사장님이 말하지 않은 사진을 넣으므로 "실제 사진 아님" 표시가 없으면 원칙 위반이다.
- 마감 전 가능 여부: 반만 가능. API 연결은 쉽지만, 표시와 메뉴 분리 규칙까지 함께 넣어야 한다.

#### 표시 필요성과 음식 오해 위험

- 국회에서 AI로 만든 음식 사진을 광고에 쓸 때 "AI로 만듦"을 밝히게 하는 법안이 나왔다. 표시를 지우거나 속이면 안 되고 플랫폼이 지워야 한다는 내용이다. (출처: https://www.chosun.com/english/market-money-en/2025/11/06/YWZ4HMALTVGHHHGBAFKOVKERWY/ / 확인 날짜: 2026-09-26)

- 배달 앱에서 AI로 만든 덜 익은 치킨 사진으로 환불을 요구하는 사례가 나왔다. 눈으로 진짜와 가짜를 가르기 어렵고, 정보가 지워지면 찾기 어렵다고 업계에서 말했다. (출처: https://www.asiae.co.kr/en/article/2026061908400465555 / 확인 날짜: 2026-09-26)
- 결론: 음식 AI 그림은 실제 메뉴처럼 보이면 손님을 속인 광고가 될 수 있다. "실제 가게 사진 아님" 표시가 꼭 필요하다. 표시해도 맛과 양이 다르면 분쟁이 생길 수 있다.
- 품질: 배경과 분위기는 쓸 만하지만, 음식 디테일은 틀리기 쉽다. (출처: 확인 못 함. 모델별 실측 필요)
- 법적 위험: 높음.
- 비용: 확인 못 함. 무료 체험 뒤에는 라이선스와 서버 비용이 든다.
- 구현 난이도: 중간. 모델 연결보다 표시, 승인, 삭제 흐름이 더 어렵다.
- 원칙 충돌: 큼. 없는 사실을 만드는 것과 같다.
- 마감 전 가능 여부: 어려움. 음식에는 쓰지 말고, 배경용으로만 따로 검토하는 것이 좋다.

### 2.6. (e) 조합안

- (a)를 맨 앞에 둔다. (c)는 배경과 분위기용으로만 쓰고 메뉴에는 쓰지 않는다. (b)는 사진 가져오기가 아니라 위치와 전화번호 확인 돕기로만 쓴다. (d)는 음식에 쓰지 않는다.
- 모든 외부 사진과 AI 그림은 사장님이 "이걸로 쓸게요"라고 고른 뒤에만 쓴다. 고르기 전에는 예시 그림으로 둔다.
- 대표 사진과 메뉴 사진은 사장님 사진만 쓴다. 스톡과 AI는 "예시" 표시를 붙이고 메뉴판에는 안 넣는다.

## 4. 추천 전략 1개와 실행 계획

### 4.1. 추천: "실제 사진 먼저, 예시는 분명히, 외부는 확인 뒤에만"

- 1순위: 대화 초반에 식당, 카페, 펜션은 사진을 필수처럼 요청한다. 대표 1장, 메뉴 2장, 가게 안팎 1장을 권한다.
- 2순위: 사진이 없으면 예시 그림으로 만들되, 시안과 공개본 모두 "예시" 표시를 분명히 한다. 지금처럼 공개본에서 표시를 숨기지 않는다.
- 3순위: 스톡은 배경과 분위기용으로만 쓰고, 메뉴와 대표에는 쓰지 않는다. 쓸 때는 "예시 사진"과 출처를 붙인다.
- 4순위: AI 음식 그림은 쓰지 않는다. 배경용만 따로 검토한다.
- 5순위: 웹 검색은 사진을 가져오는 데 쓰지 않는다. 가게 이름과 위치 확인 돕기와 "이 가게 맞나요?" 확인에만 쓴다. 사장님이 고른 뒤에만 반영한다.

### 4.2. 마감 전 (2026-09-28까지)

1. 사진 질문을 맨 앞으로 당긴다. 식당, 카페, 펜션은 가게 이름 다음에 바로 묻는다.
2. 사진 버튼 안내를 쉽게 바꾼다. "휴대폰으로 지금 찍어 올려도 돼요. 대표 1장만 있어도 사이트가 확 달라져요."라고 쓴다.
3. 사진이 없으면 시안 맨 위에 "사진이 없어 예시 그림으로 만들었어요. 사진 버튼으로 올리면 바로 바뀌어요."를 보여준다.
4. 공개본에서 예시 표시를 숨기지 않게 바꾼다. 방문자도 예시임을 알게 한다. 지금은 공개본에서 숨기므로 고쳐야 한다. (출처: app/services/site_render.py 739-740 / 확인 날짜: 2026-09-26)
5. 메뉴에 스톡과 AI 그림이 들어가지 않게 막는다. 대표와 메뉴는 사장님 사진만 받는다.
6. 공개 전 확인에 사진을 넣는다. "대표 사진이 비어 있어요. 올리거나 예시로 공개할까요?"라고 한 번 더 묻는다.

### 4.3. 마감 뒤

1. "이 가게 맞나요?" 확인 흐름을 만든다. 카카오와 구글에서 찾은 가게 후보를 보여주고, 사장님이 고르면 위치와 전화번호만 채운다. 사진은 가져오지 않는다.
2. 사장님 인스타그램 연결을 만든다. 본인 계정에서 고른 사진만 가져온다. 남의 사진은 안 가져온다.
3. 스톡 고르기 화면을 만든다. 배경용만 보여주고, 고르면 "예시 사진" 표시와 출처가 같이 들어간다.
4. 사진 심사를 만든다. 흔들리거나 어두운 사진은 다시 찍게 안내하고, 메뉴 이름과 사진이 맞는지 확인한다.
5. 삭제 요청 대응을 만든다. 남의 사진이 들어오면 바로 뺄 수 있게 한다.

### 4.4. 필요한 사용자 결정 목록

1. 식당, 카페, 펜션에 사진을 필수처럼 물을까요? 사진을 안 올리면 공개를 막을까요, 예시로 공개하게 할까요?
2. 공개본에도 "예시 이미지" 표시를 둘까요? 둔다면 문구를 "예시 이미지"로 할까요, "사장님 사진 준비 중"으로 할까요?
3. 스톡 사진을 쓸까요? 쓴다면 배경용으로만 쓸까요? 메뉴에는 절대 쓰지 않기로 할까요?
4. AI 음식 그림을 완전히 금지할까요? 배경용만 허용할까요?
5. 웹 검색으로 사진을 가져오는 것을 금지로 확정할까요? 위치 확인용 검색까지만 허용할까요?
6. 구글 Places 사진을 쓴다면, 비용 상한을 얼마로 할까요? 표시 의무와 삭제 대응을 누가 맡을까요?
7. 인스타그램 연결을 만들까요? 본인 사진만 가져오기로 할까요?
8. 마감 2026-09-28에는 (a)와 예시 표시 고치기까지만 하고, 나머지는 뒤로 미뤄도 될까요?

## 5. 출처와 확인 여부 정리

- 코드와 문서 주장은 파일 경로와 줄 번호로 적었다. 확인 날짜는 모두 2026-09-26이다.
