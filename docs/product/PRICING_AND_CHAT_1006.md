# 손님 채팅·스탬프 원가와 가격 재검토, 공개 뒤 편집 (PRICING_AND_CHAT_1006)

> 2026-10-06 (KST) / Claude. 대표 질문 3건에 대한 확인·계획:
> ① 손님 채팅을 어디서 켜고, 손님 화면을 미리 볼 수 있나. 설정 안내·결제 안내·이용요금을 정하자.
> ② 그걸 사장님 카카오톡 채팅방으로 오게 할 수 있나.
> ③ 스탬프도 돈이 드는데 소상공인 부담이 안 되게 수수료를 최소로, 서버 유지비 기준으로 가격 조정.
> ④ 공개된 사이트를 편집할 수 있나, 편집한 것이 다시 공개되는 구조인가.
> 가격 숫자는 **제안**이다. [BUSINESS_STRATEGY](BUSINESS_STRATEGY.md) §4·[FEATURE_PLATFORM_PLAN](FEATURE_PLATFORM_PLAN.md) §9를 원가 기준으로 다시 묶었다.

## 0. 결론

1. **손님 채팅은 이미 켜고 끌 수 있다** — 사장님 화면 > 채팅 탭의 "받기: 켜짐/꺼짐"(기본 켜짐). 코드: `GET·POST /api/owner/shops/{key}/chat-settings`.
2. **다만 손님 화면을 미리 볼 길이 없다.** 채팅 탭에 손님 화면(`/chat/<가게키>`) 링크가 0개다. 대표가 "대략적인 UI를 볼 수 없나"라고 느낀 지점이 정확히 이것이다 → §1.2에서 고친다(반나절).
3. **스탬프는 우리에게 원가가 거의 없다.** 우리 DB에 도장을 쓰는 것뿐이다. 돈이 드는 것은 ① 손님에게 보내는 알림(문자·알림톡) ② 카드 결제 수수료(카드사·포트원이 가져간다)다. 그래서 **스탬프에 월 4,900원을 따로 받을 원가 근거가 없다** → 기본에 넣는다.
4. **가격 원칙을 바꾼다: "원가 0인 기능은 기본에, 건당 원가가 드는 것만 실비 사용량."** 기능마다 추가금을 붙이면 소상공인이 가장 싫어하는 모양이 되고, 우리 원가와도 안 맞는다 → §5 제안.
5. **공개 뒤 편집·재공개는 이미 된다.** 고치면 그 자리에서 공개본을 다시 그린다(`app/api/card.py` `post_change_followup`). 따로 "다시 공개하기"를 누를 필요가 없다 → §6.
6. **카톡 안에서 답장까지는 아직 안 된다.** 지금은 "새 채팅이 왔어요" 알림만 사장님 카톡으로 가고(나에게 보내기, 무료) 답은 사장님 화면에서 한다. 카톡 대화창에서 주고받으려면 카카오톡 채널 + **상담톡**(유료)이 필요하다 → §2.

## 2. 사장님 카카오톡으로 받기 — 어디까지 되나

| 방법 | 지금 | 비용 | 답장까지? | 준비물 |
|---|---|---|---|---|
| 카톡 "나에게 보내기" | **됨**(`notify.owner_kakao`) | 무료 | ❌ 알림만. 링크를 눌러 사장님 화면에서 답한다 | 카카오 로그인 + 메시지 전송 동의 |
| 웹 푸시(휴대폰 알림) | **됨** | 무료 | ❌ 알림만 | 없음(브라우저 허용) |
| **알림톡** | 코드는 솔라피로 붙어 있음(문자와 같은 API) | 건당 약 7~13원 | ❌ 알림만 | 사업자등록증 + 카카오 비즈니스 채널 + 템플릿 심사 |
| **상담톡**(카톡 대화창에서 주고받기) | ❌ 없음 | **확인 필요**(채널 + 상담톡 요금제, 보통 월 기본료 + 건당) | ✅ 사장님이 카톡에서 바로 답장 | 비즈니스 채널 + 상담톡 계약 |

**판단**: 대표가 원하는 "카톡 채팅방으로 와서 거기서 답한다"는 **상담톡 영역**이다. 베타(사장님 ~10명)에서는 지금 모양(푸시·카톡 알림 + 사장님 화면 답장)으로 충분하고, 정식 오픈 전에 상담톡 요금을 조사해 "프로 요금제 기능"으로 올릴지 정하는 것이 맞다. [OWNER_NOTIFY_PLAN](OWNER_NOTIFY_PLAN.md) §9.2가 이미 경고한다: **"나에게 보내기"는 카카오 정책상 서비스→사용자 알림 용도가 아니므로 정식 오픈 전에 알림톡으로 옮겨야 한다.**

> 확인 필요(대표 또는 Claude 조사): 상담톡 월 기본료·건당 단가, 채널 1개로 여러 가게를 받을 수 있는지(아니면 가게마다 채널이 필요한지 — 가게마다면 소상공인 부담이 커져 채택하지 않는다).

## 3. 스탬프는 왜 원가가 (거의) 0인가

| 동작 | 우리 비용 |
|---|---|
| 도장 적립·쿠폰 발급·사용 처리 | DB 쓰기 몇 줄 → 사실상 0원 |
| 쿠폰 바코드 | 서버에서 그림 생성 → 0원 |
| **손님에게 "쿠폰이 나왔어요" 알림** | 문자·알림톡 건당 원가 발생 |
| **주문·결제로 도장을 적립** | 카드 결제 수수료(카드사·포트원). 우리 몫 아님 |

즉 스탬프에서 돈이 새는 곳은 **알림과 결제**뿐이다. 그래서 스탬프·쿠폰·회원 명단은 **기본에 넣고**, 알림만 사용량으로 받는 것이 원가와 맞는다.

**지금 고정비가 사실상 0원**이라는 사실이 중요하다. 가격을 낮게 잡아도 적자가 나지 않고, 비싸게 받을 근거도 없다.

## 5. 가격 제안 (원가 기준으로 다시 묶음)

### 5.1 원칙 네 줄

1. **원가 0인 기능은 기본(무료)에 넣는다** — 홈페이지·호스팅·문의·손님 채팅·웹 푸시·스탬프·쿠폰·회원 명단.
2. **건당 원가가 드는 것만 사용량으로 받는다** — 알림톡·문자·AI 초과. 선불 충전에서 차감하고, 잔액 0이면 무료 수단(웹 푸시)으로 내려간다(멈추지 않는다).
3. **고정 구독은 "브랜드와 편의"에만 받는다** — 내 도메인, "제작" 표시 제거, 고치기 무제한, 직원 계정.
4. **손님 결제 중개수수료는 0원을 유지한다** — 카카오헤어샵 25% 같은 모양을 만들지 않는 것이 우리 차별점이다([BUSINESS_STRATEGY](BUSINESS_STRATEGY.md) §3).

### 5.2 제안 표 (현행 가설과의 차이를 ▲▼로)

| | 무료 | 가게 월 **9,900원** ▼(현행 19,900) | 프로 월 **24,900원** ▼(현행 39,900) |
|---|---|---|---|
| 홈페이지·호스팅·문의·웹 푸시 | ● | ● | ● |
| **손님 채팅**(AI 답 포함) | ● 월 300건 | ● 월 1,000건 | ● 월 3,000건 |
| **스탬프·쿠폰·회원 명단** | ● ▲(현행 추가 4,900원) | ● | ● |
| 디자인 고치기 | 월 5회 | 무제한(적정 사용) | 무제한 |
| 예약 | ● ▲(현행 추가 9,900원) | ● | ● |
| 온라인 주문·결제 | — | ● ▲(현행 추가 9,900원) | ● |
| 내 도메인·"제작" 표시 없음 | — | ● | ● |
| 알림톡 포함 | — | 월 100건 | 월 500건 |
| 초과 알림톡·문자 | 선불 충전 차감(건당 **15원**) | 같음 | 건당 **12원** |
| 직원 계정 | 1명 | 3명 | 10명 |
| 손님 결제 중개수수료 | **0원** | 0원 | 0원 |

바뀐 이유: 스탬프·예약을 추가금에서 기본으로 내렸다(원가 0). 대신 구독료를 낮춰 "기능마다 돈 내는 느낌"을 없앴다. 월 9,900원은 우리 고정비(지금 0원)를 충분히 덮고, 사장님에게는 "커피 두 잔"이다.

### 5.3 회수 영향 (대략)

[BUSINESS_STRATEGY](BUSINESS_STRATEGY.md) §4는 평균 월 35,000원을 가정했다. 이 제안은 평균이 **월 12,000~15,000원**쯤으로 내려간다(무료 비중 포함). 제작비 99,000원을 유지하면 회수 기간이 길어지므로, 둘 중 하나가 필요하다.

| 보완 | 내용 |
|---|---|
| ① 제작비 유지 + 구독 저가 | 첫 달에 99,000원을 받고 구독을 낮게 유지. **추천** — 소상공인은 "한 번 내고 싸게 쓰는" 모양을 잘 받아들인다 |
| ② 가게 수로 회수 | 구독 저가 + 제작비 할인으로 가게 수를 늘린다. 서버가 0원이라 한계비용이 거의 없다 |
| ③ 프로 가치를 올린다 | 상담톡(§2)·다국어·전문 디자인을 프로 전용으로 |

## 6. 공개 뒤 편집 → 재공개 (이미 동작)

| 질문 | 답 | 근거 |
|---|---|---|
| 공개된 사이트를 편집할 수 있나 | **된다.** 세 길: ① 내 프로젝트 > "고치기" ② `/editor?room=` 직접 편집 화면 ③ 빌더 | 커밋 `fd98347`, [EDIT_PUBLISH_PLAN](EDIT_PUBLISH_PLAN.md) |
| 편집한 것이 다시 공개되나 | **자동으로 된다.** 카드가 바뀌고 이미 공개 상태면 그 자리에서 공개본을 다시 그린다. "다시 공개하기"를 누를 필요 없다 | `app/api/card.py` `post_change_followup`: `if changed and card.get("published"): design.publish_choice(...)` |
| 공개 전 편집은 | 시안 그림에 반영한다 | 같은 함수의 `elif` 갈래 |
| 위험한 편집은 막히나 | 게시 전 검사 5종(외부 스크립트·폼·자동 이동·열쇠·우회 iframe)에 걸리면 400으로 막고 사장님에게 알린다 | `publish_check.PublishBlockedError` |
| 사진·주소를 고치면 | 주소는 카카오로 좌표를 다시 맞추고, 새 항목은 태그 사진을 뒤에서 만든다 | 같은 함수 |

**남은 빈 곳**: 공개본에 "마지막으로 고친 때"가 보이지 않는다. 사장님이 "반영됐나?"를 확인할 길이 화면에 없다 → 채팅방·편집 화면에 "방금 공개본에 반영했어요"는 뜨지만(시스템 메시지), 공개 사이트 쪽 표시는 없다. 작게 넣을 수 있다(반나절, 선택).
