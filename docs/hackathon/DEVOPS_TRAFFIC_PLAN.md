## 1. 현재 구조의 트래픽 한계 진단 (전부 추정 — 부하테스트 미실시)

> 전제: 아래 숫자는 코드·스펙으로부터의 추론이며 **실측 부하테스트 없이는 정확한 숫자를 모른다.**
> "몇 명까지 버틴다"는 어떤 단언도 테스트로 검증된 사실이 아니다.

### 1.1 병목 지점 — 어디서 먼저 무너지는가 (무너지는 순서대로)

| 순서 | 병목 | 이유 | 예상 증상 |
|---|---|---|---|
| **① (첫 번째)** | **코드생성 동시 실행 수 무제한** | `start_codegen`에 세마포어 없음. 요청 N개 → `hermes-sandbox` 컨테이너 N개 병렬 기동(Hermes 풀스택: python venv + node, 이미지 2.68GB). `--memory`/`--cpus` 제한도 없어 호스트 12GB를 N개가 나눠 먹음. 타임아웃 좀비 정리도 없어 실패할수록 잔류 컨테이너가 메모리를 계속 점유 | 동시 코드생성 3개 이상에서 (추정) 응답 90초 타임아웃 연쇄 → OOM kill 시 호스트 전체(Flask 본체 포함) 불안정. **가장 먼저, 가장 크게 무너지는 지점** |
| ② | **스크린샷 Chromium launch (요청 스레드 blocking)** | `QUOTED → 진행` 1회마다 Chromium launch(~1-3초 추정) + NIM 호출이 요청 스레드에서 순차 실행. `threaded=True`라 다른 요청이 아주 막히진 않지만, 동시 `진행` 요청이 몰리면 스레드·메모리가 같이 잠김 | 견적 승인 타이밍이 겹치면 (추정) 수 초~수십 초 응답 지연 |
| ③ | **Flask 개발 서버 단일 프로세스** | `threaded=True`는 스레드 기반 병행이라 가벼운 채팅·폴링은 감당. 그러나 시그널 드레인·워커 격리가 없어, ①·②처럼 "스레드를 오래 붙잡는" 요청이 쌓이면 스레드 고갈 → 전체 무응답. 개발 서버라 프로덕션 수준의 큐잉·백프레셔 없음 | 장시간(90초) 코드생성 폴링 + NIM hang이 겹치면 (추정) 신규 요청까지 지연 전파 |
| ④ | **NIM API 레이트리밋·지연** | 매 대화턴 임베딩 1회 + 견적 chat 1회 + 코드생성당 Hermes NIM 호출. 견적 캐시 없음(같은 질문 반복해도 매번 호출). NIM 측 hang은 25초 타임아웃+폴백으로 완화 완료했으나, 레이트리밋(429)이 걸리면 폴백 견적(정적)으로만 응답하게 되어 데모 품질 저하 | 트래픽 급증 시 (추정) 과금 증가 + 일부 요청이 폴백 응답으로 격하 |
| ⑤ (마지막) | 인메모리 세션 + 파일 저장 | 락(`SESSIONS_LOCK`/`ROOMS_LOCK`)은 단일 프로세스 내에서는 유효. 단일 인스턴스·단일 프로세스 전제에서는 동시 사용자 수십 명 수준의 읽기/쓰기(4초 폴링)는 감당 (추정). 프로세스를 2개로 늘리는 순간 깨지므로, 단일 프로세스를 유지하는 한 병목이 아님 | 파일 전체 직렬화라 방 수백 개·메시지 누적 시에만 저하 (추정 — 데모 규모와 무관) |

### 1.2 동시 사용자 추정치 (추정 — 검증 없음)

| 시나리오 | 판단 (추정) | 근거 |

## 3. 트래픽이 실제로 몰렸을 때의 운영 절차 (코드 변경 없이 할 수 있는 것)

> 시연 당일(여러 외부 평가자 동시 접속) 기준. 아래는 **지금 구조 그대로** 실행하는 절차다.

### 3.1 시연 직전 워밍업 (소요 ~10분, $0)

1. `scripts/check_oci_cost.sh`로 당월 누적 비용 확인 ($0대인지, Budget $5 대비 여유 확인).
2. `scripts/deploy.sh`로 최종 배포 → `warmup.sh` 헬스 통과 확인. **시연 1시간 전부터는 배포 금지** (DEPLOYMENT_STRATEGY §5-1).
3. 워밍업 요청 1회: 방 생성 → 메시지 1턴(RAG 임베딩 캐시 적재) → 승인 → 견적(NIM 경로 예열). 데모용 입력 2~3개는 미리 돌려 **견적 캐시(§2-② 적용 완료라면)에 적재**.
4. 원격에서 1회 실측 (DEPLOYMENT_STRATEGY §5-1 권장): `docker stats --no-stream` + `docker images` + `df -h` — 메모리 여유·좀비 컨테이너·디스크를 눈으로 확인. 좀비(`codegen-*` 잔류)가 있으면 `docker stop` + `docker rm`으로 사전 정리.

### 3.2 동시접속 모니터링 방법 ($0, 도구 추가 없음)

| 수단 | 명령/위치 | 보는 것 |
|---|---|---|
| 헬스체크 | `curl http://144.24.91.250:8643/health` (시연용 노트북에서 주기 실행) | 200이 아니면 즉시 §3.3으로 |
| 컨테이너 상태 | `ssh → sudo docker stats --no-stream` + `sudo docker ps` | backend 메모리 급증, `hermes-sandbox` 형제 컨테이너 개수(=진행 중 코드생성 수). **3개 이상이면 위험 신호 (추정)** |
| 로그 | `ssh → sudo docker compose logs --tail 50 backend` | `[build_quote] NIM 호출 실패`, `[save_sessions] 실패`, TimeoutExpired 흔적 |

### 3.3 문제 생겼을 때 즉시 재시작 절차 ($0, 수십 초)

1. **Flask 무응답** (`/health` 실패): `ssh → cd ~/agt001 → sudo docker compose restart backend` → `warmup.sh` 통과 확인. 세션은 파일 백업에서 복구되며, `GENERATING`이던 세션은 `QUOTED`로 되돌아가 "진행 재전송" 안내로 이어짐 (backend.py:67-73 복구 규칙).
2. **코드생성만 멈춤** (대화는 되는데 GENERATING이 90초+ 안 끝남): 해당 요청은 타임아웃 후 자동 `QUOTED` 복귀 + "다시 진행" 안내가 나가므로 **기다린다**. 무응답이 길어지면 `docker ps`에서 잔류 샌드박스를 `docker stop -t 5 <name>` 후 같은 방에서 "진행" 재전송.
3. **메모리가 임계** (`docker stats`에서 여유 <1GB 추정): 잔류 샌드박스 정리 → 그래도 안 되면 backend 재시작(§3.3-1). **시연 중 배포(`--build`)는 금지** — 재시작만 한다.
4. 롤백 수단: `rollback.sh`는 아직 없으므로(§0), 장애가 특정 배포 직후라면 로컬에서 **직전 커밋 체크아웃 → `deploy.sh` 재실행** (수동 롤백, 수 분). DEPLOYMENT_STRATEGY 안 C(`rollback.sh` 최소 구현)는 마감 후 백로그.

### 3.4 트래픽이 과도하면 신규 요청을 일시적으로 막는 방법 ($0, 코드 변경 없음)

- **시연용 방 1개로 유도**: 외부 평가자 전원을 같은 방에 입장시켜 방(세션) 1개로 합류 — 방마다 상태머신·코드생성이 따로 도는 구조이므로, 방을 하나로 묶는 것만으로 코드생성 동시 실행을 자연스럽게 직렬화할 수 있다. 투표 과반 규칙상 1개 방이 오히려 데모 흐름에도 유리.
- **코드생성 순번제 안내**: "코드생성은 한 조씩 순서대로 눌러주세요"를 사회자 멘트로 고정 — 세마포어(§2-①) 적용 전까지의 임시 가드레일.
- **보안리스트 임시 차단** (최후 수단): OCI 콘솔/CLI에서 TCP 8643 인그레스 규칙을 시연 관계자 IP로 한시 축소 — 무관 트래픽(크롤러·우연 접속) 차단. 단, **외부 포트 체계 변경이 아니라 규칙 source만 좁히는 것**이며, 시연 직후 원복한다. (규칙 자체를 지우거나 포트를 바꾸면 sslip.io·카카오 도메인 등록이 깨지므로 금지 — DEPLOYMENT_STRATEGY §5-3.)
- **정적 폴백 안내**: NIM 장애·과부하로 폴백 견적이 나가면 "기본 견적"임을 숨기지 말고(응답문에 명시됨) 구두로 보충 — EFFICIENCY_PLAN의 폴백 설계가 의도한 운용이다.
