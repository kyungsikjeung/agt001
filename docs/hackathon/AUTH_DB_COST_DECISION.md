## TL;DR (전체 요약)

- 지금 구조(`backend.py`의 `ROOMS`/`SESSIONS` + `generated/rooms.json`, 닉네임 자칭식, 인증 없음)에 로그인을 붙이려면 **계정 저장소 + 게스트→계정 merge API + 로그인 UI가 최소 세트**이며, 비밀번호를 다루는 순간 현행 JSON 파일 방식은 버티기 어렵고 **SQLite 최소 전환이 필요**하다 (PostgreSQL/관리형 DB는 과잉).
- 사용자가 명시한 핵심 시나리오(게스트로 견적까지 → 로그인 시 이어받기)는 기술적으로 가능하며, 설계안은 **`localStorage`의 게스트 ID를 로그인 시점에 계정에 귀속시키는 claim/merge 방식**이 정석이다 (상세 §1).
- 비용은 데모 규모에서 월 **$0 유지 가능 (추정)** 이나, 진짜 변수는 인프라가 아니라 **NIM 사용량 과금 + 마감 5일 전의 공수 리스크**다.
- 권장 결론은 **No-Go (9-28 마감 전에는 넣지 않는다)** 이며, 마감 후 1순위 백로그로 "최소 범위안(결과 저장만 회원 + 카카오 로그인 + SQLite)"을 제안한다. 근거는 §5.

## 1. 회원가입/로그인 플로우 설계

### 1.1 현행 구조 확인 (실측, `backend.py` 기준)

- 방 생성: `POST /room` → `room_id`(8자리) + 신규 `session_id` 발급, `ROOMS[room_id]`가 `SESSIONS[session_id]`를 **참조만** 한다 (복제 아님). 상태머신(`GREETING→…→DONE`)은 방당 1개 공유 (`backend.py:567-587`, `_process_chat_turn:676-792`).
- 입장: `POST /room/<id>/chat`에서 `member_id`(클라이언트가 만든 uuid 수준) + `nickname`(자칭, 최대 40자, `html.escape` 처리) 수신. 호출자 인증 없음. 첫 입장 시 `members[]`에 추가 + 입장 시스템 메시지 (`backend.py:590-652`).
- 조회: `GET /room/<id>/messages?since=` — 방 로그 전체를 전원에게 동일 노출 (`backend.py:655-673`).
- 영속성: 인메모리 dict가 원본 + `generated/rooms.json`·`sessions.json`에 원자 저장(tmp+rename) + 재시작 복구 (`backend.py:33-108`). 현재 로컬 `generated/`는 비어 있음(서버 기동 시 생성되는 구조).
- 프론트(`static/index.html`): `sessionId` 전역 1개, `localStorage` 미사용, 새로고침 시 대화 소실(서버 로그는 방에만 있음).

즉 현재 "나"라는 개념은 **브라우저 탭 + 자칭 닉네임**뿐이며, 서버가 기억하는 것은 `member_id` 문자열뿐이다. 이 공백을 메우는 것이 회원 설계의 전부다.

### 1.2 핵심 시나리오: 게스트 → 로그인 이어받기 (사용자 명시 요구)

요구: "회원가입 없이 먼저 이용(게스트로 요구사항 도출·견적까지 진행) → 이후 로그인/회원가입하면 게스트 때 만든 대화/견적이 그 계정에 연결".

#### 설계: guest-claim (merge) 방식

정석적인 방법은 **게스트 식별자를 로그인 시점에 계정에 귀속**시키는 것이다. 구체 순서:

```
[게스트 단계 — 로그인 없음, 현행 그대로]
1. 게스트가 방 입장 → 서버는 기존대로 member_id(A)/room_id/session_id 발급
2. 브라우저 localStorage에 저장: { guest_member_ids: [A], guest_rooms: [room_id], guest_sessions: [session_id] }
   (서버 스키마 변경 없음 — 지금 당장 프론트만으로 준비 가능)

[로그인/회원가입 단계]
3. 사용자가 로그인 (카카오 또는 이메일 — §1.4)
4. 프론트가 서버에 1회 호출:
     POST /auth/claim  { guest_member_ids: [...], guest_rooms: [...] }
     (Authorization: 로그인 세션/토큰 — 본인 계정으로만 귀속 가능)
5. 서버가 검증 후 귀속 테이블에 기록:
     guest_links: (guest_member_id → user_id), (room_id → user_id, role='participant')
6. 이후 "내 대화이력" 조회:
     GET /me/rooms  → guest_links 경유로 게스트 시절 방·견적·시안/design_url·deploy_url 반환
```

핵심 포인트:

- **게스트 단계는 서버 변경 없이 시작할 수 있다.** `localStorage`에 ID를 남기는 것만으로 "나중에 이어받기"의 재료가 된다. 이것이 이 시나리오가 "지금 해도 되는 부분 / 로그인 후에야 되는 부분"으로 쪼개지는 이유다.
- **merge는 로그인 "시점"에 1회만 일어난다.** 매 요청마다 게스트 ID를 검사하는 방식이 아니라, claim API 한 번으로 귀속을 확정하고 이후에는 `user_id` 기준으로 조회한다. 구현·검증 범위가 작다.
- **소유권 검증이 필수다.** `member_id`는 현재 자칭 문자열이라 누구나 남의 ID를 claim할 수 있다. 따라서 claim 대상은 "브라우저가 실제로 들고 있던 ID"여야 하며, 최소한 (a) claim 요청 자체가 로그인 세션 위에서 오고, (b) 1회성 귀속(재귀속 불가, 타 계정 탈취 불가) 규칙을 둔다. 더 엄밀히는 게스트 발급 시 서버가 `guest_secret`(난수)을 함께 내려주고 claim 때 함께 제시하게 한다 — 신규 필드 1개 추가 수준이다.
- **투표(`votes`)와의 정합성:** 귀속 후에도 방 로그의 `member_id`는 그대로 둔다(로그 불변). "내가 한 투표"를 계정 기준으로 보여줄 때만 `guest_links`를 경유해 매핑한다. 로그를 계정 ID로 다시 쓰지 않는다.

### 1.3 room/session과 회원 개념의 연결 — 3가지 해석안과 추천

| 안 | 내용 | 장점 | 단점 |
|---|---|---|---|
| **안 A. 방은 비회원 그대로, "결과 저장"만 회원 (추천)** | 입장·대화·투표는 현행 자칭식 유지. 로그인하면 `GET /me/rooms`로 "내가 참여한 방의 견적·시안·배포 링크"를 모아본다. 귀속은 §1.2 claim 1회 | 변경 최소(신규 엔드포인트 2~3개 + 귀속 테이블). 데모 동선(게스트 우선)에 정확히 부합. 방 로직·투표 규칙 무변경 | 방 접근제어(비공개방 등)는 불가 — 데모 범위에서는 불필요 |
| 안 B. 참여자 개인별 계정 | `members[].member_id ↔ user_id` 바인딩. 로그인 사용자는 실명/프로필 표시, 게스트는 "게스트" 뱃지 | 발신자 신뢰도↑, "누가 승인했는지"가 계정 단위로 남음 | 입장 시 로그인 압박 → 게스트 우선 흐름과 충돌. 투표·닉네임 로직 전부 손댐 |
| 안 C. 방 자체를 회원 소유 | 방 생성 시 방장 계정 필수, 방 단위 공개/비공개·추방 | 운영 기능 완비 | 방 생성에 로그인 강제 = 핵심 시나리오(게스트 먼저)와 정면 충돌. 범위 최대 |

**추천: 안 A.** 이유 3가지: (1) 사용자가 명시한 핵심 시나리오가 "게스트 먼저"이므로 입구에 인증을 두는 B/C는 요구 역행, (2) 기존 승인 게이트(과반 투표, `MULTIUSER_CHAT_DESIGN.md` §4.2)와 상태머신 공유 구조를 전혀 건드리지 않음, (3) 로그인 UI도 "결과 저장/이어보기" 한 곳에만 붙이면 되므로 프론트 변경이 국소적 (§2).

### 1.4 로그인 수단 선택지

| 수단 | 내용 | 장점 | 단점 |
|---|---|---|---|
| **카카오 로그인 (조건부 추천)** | 카카오 디벨로퍼스 앱(`agt001`, ENVIRONMENT.md §3-6) 기반 OAuth. JS 키·도메인(`sslip.io`) 등록이 이미 실측 검증됨 | 별도 가입 폼·비밀번호 저장 불필요. 이메일 발송 인프라 불필요. 기존 카카오 공유 동선과 자연스럽게 연결 | 카카오 앱 평가·동의항목(닉네임/이메일) 추가 설정 필요 (추정: 영업일 단위 소요 가능). 카카오 의존 |
| 이메일 + 비밀번호 | 직접 가입 폼 + 해시 저장 + 세션/JWT | 외부 의존 없음 | 비밀번호 해시(`werkzeug.security` 등 의존성 추가), 세션 관리, 인증메일 발송 인프라(§4), 탈퇴·재설정 플로우 — 범위 최대 |
| 소셜 기타 (구글 등) | OAuth 추가 | 선택지 확대 | 새 앱 등록·평가 — 마감 전 불가 |

**판단:** 어떤 수단을 쓰든 "DB + 세션 + claim" 최소 세트는 동일하다. 수단별 추가분만 다르며, 붙인다면 카카오 로그인이 추가분이 가장 작다 (추정 포함 — 동의항목 평가가 마감 내 끝난다는 보장은 없음).

### 1.5 최소 API·데이터 추가분 (안 A 기준, 코드 수정 아님 — 설계만)

- `POST /auth/{kakao|signup|login}`, `POST /auth/claim`, `GET /me/rooms` (신규 3~4개, 기존 `/room*`·`/chat` 무변경).
- 신규 저장소: `users`, `guest_links` (스키마 §3.3). `ROOMS`/`SESSIONS` 구조 무변경.
- 예상 공수 (추정): 백엔드 1~1.5일 + 프론트 0.5~1일 + 검증 0.5일 = **약 2~3일** — §5 판단의 핵심 입력이다.

## 2. UI/UX 재검토

### 2.1 기존 두 문서와의 정합성

- `MULTIUSER_CHAT_DESIGN.md`는 "방은 웹, 카카오는 초대 링크" (해석 C), 폴링 확장, `ai_status` 브로드캐스트, 과반 투표를 확정했고, **인증은 "무리 범위(마감 후)"로 명시**했다 (§0.2). 회원 추가는 이 문서의 전제(닉네임 자칭식, §3.6)를 바꾸는 것이므로, 넣는다면 해당 문서의 §3.6 개정부터 필요하다.
- `UIUX_DESIGN_REFERENCE.md`의 Slack식 방향(전원 좌측 정렬 + 아바타 + `[BOT]` 칩, AI 진행 카드, 투표 바)은 **회원이 추가돼도 유효하다.** 오히려 아바타·이름표 자리에 계정 프로필/실명을 꽂으면 되는 구조라 상성이 좋다. 깨지는 부분은 없고, "게스트 vs 회원" 표시 1종(뱃지)만 추가하면 된다.

### 2.2 로그인/게스트 요소 배치안 (안 A 기준)

원칙: **입구를 막지 않는다.** 게스트 우선 시나리오이므로 로그인 유도은 "결과가 생긴 시점"에만 노출한다.

| 위치 | 요소 | 비고 |
|---|---|---|
| 헤더 우측 | `[로그인]` 버튼 (미로그인 시) / 프로필 아바타 (로그인 시) | 전역 1곳. 채팅 흐름 방해 금지 |
| 채팅 상단 | 게스트 배너 1줄: "게스트로 참여 중 — 기록을 저장하려면 로그인" + `[이어받기]` | dismiss 가능, 재입장 시까지만 표시. 입력창 상단 고정 바 형태 권장 |
| 견적/AI 카드 하단 | `[이 견적 저장하기]` CTA → 미로그인 시 로그인 모달 | §1.2 claim과 연결되는 전환점. 투표 바(`UIUX_DESIGN_REFERENCE.md` §3-1)와 같은 카드 안에 두어 동선 단절 방지 |
| 별도 화면 | `내 기록` (참여 방·견적·시안·배포 링크 목록) | 로그인 후 진입. 게스트 시절 claim된 방이 여기 뜬다 |
| 입장 모달 | 닉네임 입력 유지 (자칭식 그대로) | 로그인 강제 금지 — 안 A의 핵심 |

XSS·표시 주의: 닉네임 렌더링은 기존처럼 `textContent` (현행 `static/index.html:51-57` 준수). 로그인 사용자의 카카오 닉네임도 동일 처리.

| `mobile-native` | 로그인 모달의 모바일 키보드·세이프에어리어 대응 (공유방 화면과 동일 이슈) |

제안이지 실행이 아니다 — 그리고 이 표 자체가 "할 일이 두 배"임을 보여준다.

## 3. 데이터베이스 설계

### 3.1 현행 방식의 정확한 위치 (`backend.py:33-108`)

- 인메모리 dict가 원본, JSON 파일은 재시작 복구용 백업. 원자 저장(tmp+rename), 스레드 락(`SESSIONS_LOCK`/`ROOMS_LOCK`), 재시작 시 `GENERATING→QUOTED`·`ai_status→IDLE` 복구.
- 단일 Flask 프로세스(`threaded=True`), 단일 호스트(OCI 1대) 전제. 프로세스 간 공유·트랜잭션·인덱스·쿼리 개념 없음. 파일 전체를 매번 직렬화/역직렬화한다.

### 3.2 JSON으로 계속 버틸 수 있는가 — 판단: **회원(비밀번호)을 다루면 불가**

계정-게스트 연결·계정별 이력 조회가 필요해지는 순간 JSON 방식이 깨지는 이유:

1. **비밀번호 해시를 JSON에 둘 수 없다** (실무상 불가 — 평문/가역 저장 유혹, 파일 유출 시 전 계정 탈취, 감사 불가). 소셜로그인만 쓰더라도 토큰·귀속 테이블의 무결성 요구는 동일.
2. **계정별 조회가 전수 스캔이 된다.** "내 방 목록"이 `rooms.json` 전체 로드 + 순회. 방 수백 개·메시지 누적 시 매 요청 수십 MB 파싱 (추정 — 메시지량 가정 필요).
3. **파일 전체 rewrite 경합.** 방이 늘어 폴링마다 `save_rooms()`가 돌면(현행은 채팅 POST마다 저장) 쓰기 단위가 파일 전체. 락은 단일 프로세스 내에서만 유효하고, 향후 프로세스 2개(gunicorn 등)로 늘리면 즉시 깨진다.
4. **`room.session_id` 포인터의 참조 무결성 없음.** 세션 삭제·파일 손상 시 방이 dangling. 계정 귀속(`guest_links`)이 하나 더 얹히면 깨질 고리가 셋이 된다.

### 3.3 전환한다면: SQLite + 최소 스키마안 (이 프로젝트 조건 기준)

조건: OCI Always Free 2 OCPU/12GB 정확히 한도 소진 중(여유 없음, §4.1), Docker Compose 단일 컨테이너(Flask), Python 표준 라이브러리(`sqlite3` — 의존성 추가 없음), 데모~100명 규모.

- **SQLite를 권장.** 이유: 추가 프로세스·포트·볼륨 설정 없이 파일 1개(`generated/app.db`)를 기존 볼륨에 두면 됨. WAL 모드 + 타임아웃으로 Flask 스레드 병행은 감당 가능 (추정 — 수십 동시 쓰기 기준). 백업은 파일 복사.
- **PostgreSQL/관리형 DB는 과잉.** 별도 컨테이너(메모리 압박 — 한도 소진 중) 또는 관리형(비용·설정, §4) 필요. 100명 규모 폴링 앱에 불필요.
- **최소 스키마안 (안 A 기준):**

```sql
users(id TEXT PK, nickname TEXT NOT NULL, created_at TEXT NOT NULL,
      kakao_sub TEXT UNIQUE,          -- 카카오 로그인용 (이메일 방식이면 email UNIQUE + password_hash)
      email TEXT UNIQUE);
guest_links(guest_member_id TEXT PK, user_id TEXT NOT NULL REFERENCES users(id),
      room_id TEXT NOT NULL, claimed_at TEXT NOT NULL);
-- ROOMS/SESSIONS 본체는 당장 JSON 유지 가능. 방이 수백 개를 넘으면 messages 분리 테이블을 그때 검토.
```

- 마이그레이션 순서(마감 후): (1) `users`+`guest_links`만 SQLite로, 방 로그는 JSON 유지 → (2) 필요해지면 방/메시지 이전. 1단계로 데모·100명 규모는 충분 (추정).

### 3.4 전환 안 한다면: 감수 범위 명시

- **가능한 범위:** 현행 그대로(비회원 방) + 프론트 `localStorage`로 "내가 본 방 링크"만 모아보기(서버 계정 없음, 기기 귀속). 데모 시연·10명 이하에서는 파손 없음.
- **감수 목록:** 비밀번호 저장 불가(→ 이메일 가입 불가, 소셜도 귀속 무결성 약함), 기기 변경 시 이력 소실, 방 수백 개 이후 파일 비대화·조회 저하, 다중 프로세스 확장 불가. 이 중 하나라도 필요해지면 §3.3으로 전환한다.

### 4.1 확인된 전제 (리포 실측 + 공식 문서)

- 아웃바운드: Always Free 월 10TB 포함 (공식 문서 확인 — 채팅·폴링 트래픽 수준에서는 사실상 무한대).
- NIM: ENVIRONMENT.md §5는 **"NIM API 사용량 — 별도, 이 문서 범위 밖"** 으로 명시. 즉 **리포 안에 정확한 단가 없음** — 아래 NIM 단가는 외부 프록시(OpenRouter 기반 집계) 기준 **추정**이다.

## 5. Go / No-Go 판단 근거

### 5.1 일정 사실관계 (git log 실측)

- 작성 시점: 2026-09-23 17:58 KST (최신 커밋). 마감 2026-09-28 → **약 5일 (D-5)**.
- 다인원 백엔드는 완료이나 **프론트 UI(D-3)·end-to-end 검증(D-2)이 아직 남음** (STATUS.md). 즉 남은 5일은 이미 주인 있는 일정이다.

### 5.2 찬성 이유 (Go)

1. 사용자 명시 요구(게스트→로그인 이어받기)에 직접 응답 — 데모 스토리("돌아온 고객") 완성도 상승.
2. §1.2 claim 설계상 게스트 단계는 지금도 준비 가능하고, 안 A면 기존 방 로직 무변경 — 기술적 불확실성은 낮음.
3. 한계비용 ≈ $0 (SQLite + 카카오 로그인 가정) — 돈이 막는 게 아님.
4. 평가 후 실사용을 염두에 두면 계정 체계는 어차피 필요 — 먼저 하면 이후 작업 선점.

### 5.3 반대 이유 (No-Go)

1. **공수 2~3일 (추정, §1.5)이 D-5 잔여 일정의 주인 있는 슬롯(프론트+검증)과 정면 경합.** 다인원 프론트 지연 → 데모 전체 리스크로 전이.
2. 인증은 **실패 시 데모가 죽는 종류의 기능**이 아니라 **실패하면 보안 사고가 나는 종류**다 (비밀번호·세션·귀속 탈취). 마감 전 급조는 품질 부채가 아니라 보안 부채.
3. 기존 문서 2종(`MULTIUSER_CHAT_DESIGN.md` §0.2의 "인증은 무리 범위", PM 플랜의 스킬 슬롯)이 모두 "이번에 안 한다" 전제로 짜여 있음 — 뒤집으면 설계·PM 문서부터 개정.
4. 비용 측면 이득이 없음 — S0/S1에서 회원 유무가 월 비용을 바꾸지 않음 (§4.3). 즉 "지금 넣을 금전적 이유"가 없다.

### 5.4 선택지와 권장 결론

| 선택지 | 내용 | 평가 |
|---|---|---|
| 넣는다 (풀 스코프) | 이메일+소셜+내 기록+접근제어 | 반대 1~3으로 기각 권장 |
| **최소 범위로 넣는다** | 안 A + 카카오 로그인 + SQLite + claim 1회 | 기술적으로는 가능하나, 여전히 2~3일 (추정). 마감 후라면 최선안 |
| **안 넣는다 (권장)** | 9-28까지 비회원 방 그대로. 대신 (a) 프론트 `localStorage`에 게스트 ID 저장만 미리(서버 변경 없음, §1.2 절차 2) + (b) 로그인/게스트 배너 자리만 UI에 예약 | 데모 리스크 0, 마감 후 최소 범위안으로 자연 연결 |

**권장 결론: No-Go — 9-28 마감 전에는 회원가입/로그인을 넣지 않는다.** 단, §1.2의 게스트 ID `localStorage` 저장(서버 무변경)과 §2.2의 로그인 진입점 자리(UI 예약)만 다인원 프론트 작업 안에 포함하면, 마감 다음 날부터 "최소 범위안(안 A + 카카오 로그인 + SQLite)"으로 착수할 수 있다. 최종 결정은 사용자에게 있다 — 이 문서는 판단 근거 제공이 목적이며, "이렇게 하겠다"는 단정을 대신하지 않는다.

### 5.5 마감 후 백로그 (No-Go 선택 시의 다음 순서)

2. 카카오 로그인 + `POST /auth/claim` + `GET /me/rooms` (안 A).
3. 게스트 배너·저장 CTA·내 기록 UI (§2.2) + 스킬 감수 (§2.3).
