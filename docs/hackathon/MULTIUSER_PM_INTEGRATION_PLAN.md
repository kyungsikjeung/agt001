## 0. PM 판단 — 이 기능을 지금 넣는 게 맞는가

사용자가 명시적으로 "신규 기능 추가할꺼야"로 확정했으므로 찬반 재론은 하지 않는다. 대신 PM으로서 할 일은 **"완성도 있게 넣되, 이미 끝난 9단계 파이프라인을 망가뜨리지 않는 통합 방식"**을 정하는 것이다. `EFFICIENCY_PLAN.md`가 마감 전 대규모 신규 기능을 경고한 이유(리스크 급증)는 여전히 유효하므로, 그 리스크를 낮추는 방향으로 스코프를 좁힌다.

**핵심 전략 결정 (지금 확정, 조사 결과와 무관하게 유효):**

- **기존 1:1 파이프라인은 절대 건드리지 않는다.** `SESSIONS[session_id]` 구조·`/chat` 상태머신·팀A/B/C 로직은 그대로 두고, 다인원 기능은 **그 위에 얹는 별도 경로**로 만든다. 실패해도 기존 데모가 죽지 않도록.
- **"카카오톡 안에서 그룹+봇"은 십중팔구 공식 API로 불가능하다** (카카오톡 채널 챗봇은 1:1 상담톡 전제, 오픈채팅에 봇을 넣는 공식 경로는 없음 — `MULTIUSER_CHAT_DESIGN.md` 조사로 최종 확인 예정). 그래서 **"우리 웹에 room(방) 개념을 만들고, 카카오톡은 그 room 링크를 참여자들에게 공유하는 용도"**로 방향을 미리 잡는다. 이게 틀리면(조사 결과 다르게 나오면) §2에서 수정한다.
- **AI 처리 가시화는 이미 있는 GENERATING 폴링 상태를 재사용**한다 — 새로 만들지 않는다. 지금도 "코드 생성 중입니다" 메시지가 있으니, 이걸 room의 전 참여자에게 보이게 확장하면 된다.

## 3. 아키텍처 통합 방식 (MULTIUSER_CHAT_DESIGN.md §3 확정)

```
기존:  SESSIONS[session_id] = {state, requirement_id, last_request, quote, ...}  (1인, 무변경)
신규:  rooms[room_id] = {
         room_id, session_id,           # session_id로 기존 SESSIONS 항목을 그대로 참조 (복제 아님)
         members: [{member_id, nickname, joined_at, last_seen}],
         messages: [{seq, member_id|"ai", nickname, text, ts, kind}],  # append-only 로그
         ai_status: IDLE|RAG_SEARCHING|THINKING|QUOTING|GENERATING|DONE,
         votes: {member_id: approve|reject}
       }
```

- **기존 `/chat`은 절대 건드리지 않는다.** 신규 엔드포인트 3개만 추가: `POST /room`(방 생성), `POST /room/<id>/chat`(발화 전송), `GET /room/<id>/messages?since=<seq>`(증분 조회). 상태머신(`GREETING→...→DONE`) 본체는 방마다 복제하지 않고 1개를 공유 — 방 참여자 N명의 발화가 모두 같은 상태머신 입력으로 들어가고, AI 응답 1개가 방 전체에 브로드캐스트된다.
- **폴링은 4초 그대로, 프로토콜만 분리.** 지금의 "난수 메시지로 상태만 조회" 패턴은 공유방에서 로그 오염이 되므로, 전송(`POST .../chat`)과 조회(`GET .../messages`)를 나눈다. WebSocket/SSE는 채택하지 않음 — Render 무료 티어 장시간 연결 상성 문제 + `Dockerfile.backend` 재빌드 필요(EFFICIENCY_PLAN §2 "Dockerfile 동결" 원칙과 충돌) + 마감 내 편익 대비 리스크 과다.
- **`SESSIONS_LOCK`과 동일 패턴으로 `ROOMS_LOCK` 추가.**
- **`save_sessions()`/`load_sessions()` 패턴을 그대로 확장**해 `rooms`도 같은 원자 저장(tmp+rename)에 포함. `GENERATING→QUOTED` 재시작 복구 규칙도 방 단위로 동일 적용.
- **`ai_status`는 기존 동기 호출 지점에 대입 1줄씩 추가**하면 된다 (`rag_precheck` 진입 시 `RAG_SEARCHING`, `call_nim` 전 `THINKING`, `build_quote` 진입 시 `QUOTING`, 기존 `GENERATING` 그대로 대응). 동기 구간은 상태를 먼저 기록하고 저장한 뒤 작업을 시작해야 폴링하는 타인이 중간 상태를 볼 수 있다.
- **승인 게이트(⑦)**: `AWAIT_APPROVAL`의 본체 로직(`build_quote` 호출, 상태 전이)은 한 줄도 안 바뀐다 — 바뀌는 건 "그 본체로 들어가는 조건"뿐. `votes` dict에 찬성/반대를 기록하고 시스템 메시지로 투표 현황을 방 전원에 공개, 찬성 과반이면 기존 승인 경로, 반대 과반이면 기존 거절 경로, 동점은 대기.
- **BND-1 스키마**: `customer_id`(기존, 방 생성자) 유지 + `room_id`·`approved_by`를 optional로 추가 — `additionalProperties: true`라 하위 호환.

이 방식의 장점: **이번 주에 이미 검증된 3개 패턴(락, 파일백업, 폴링)을 그대로 재사용**하므로 새 리스크는 "room 데이터 모델"과 "프론트 다인원 렌더링" 두 곳으로 좁혀진다. 기존 상태머신·승인 본체·팀B/C 로직은 전부 무변경.

## 4. UI 구현 (UIUX_DESIGN_REFERENCE.md 확정 — Slack식 방향 채택)

**확정된 디자인 방향**: Slack식 "아바타+이름 좌측 정렬 + 스레드" + Slack AI Agent식 "전원에게 보이는 단계별 진행 카드" + Slack식 "이모지 투표 합의" 조합. 카카오 그룹채팅 특유의 좌우 버블 UI는 채택하지 않는다(발신자가 3명 이상이면 "누가 AI인지" 구분이 어려워짐 — UIUX_DESIGN_REFERENCE.md §1-4).

- **좌우 버블 폐기 → 전원 좌측 정렬 + 아바타 + 이름표.** 기존 `.user{text-align:right}`/`.bot{text-align:left}` 구조 대신, 모든 메시지가 좌측 정렬되고 발신자 아바타(원형)+이름+타임스탬프가 붙는다. AI는 "🤖 요구사항봇" + `[BOT]` 칩으로 고정 구분(Discord식 뱃지 차용).
- **AI 처리는 단계별 진행 카드로, 전원에게 동일 노출.** 단순 "생성 중" 고정문 대신 `① 대화 수집 → ② 중복 제거/충돌 탐지 → ③ 요구사항 초안 작성` 같은 3단계 카드(○ 대기/◐ 진행중/● 완료)를 `ai_status` 필드 갱신에 맞춰 표시. 카드 제목에 "OO님의 요청으로 정리 중"을 명시해 다른 참여자의 혼란을 막는다(ChatGPT Agent·Slack Agent 공통 패턴).
- **합의는 이모지 투표 바로.** AI 정리 카드/견적 카드 하단에 `[👍 확정 2/3] [🔁 다시]` 형태의 투표 바. §3의 `votes` dict를 그대로 이 UI로 노출하면 된다 — 새 데이터 구조 불필요.
- **AI 응답이 스트리밍이 아니라 폴링이므로(§3, WebSocket 미채택)**, "스트리밍 커서" 패턴 대신 "카드 상태 갱신"만 채택한다 — TTFT 체감 개선은 이번 스코프에서 제외(스트리밍은 마감 후 과제).
- 입장은 `?room=<id>` 링크 접속 → 닉네임 입력(prompt 수준, 계정/인증 없음) → 즉시 전체 로그(`since=0`) 로드.
- XSS 방지: 기존 프론트처럼 닉네임도 반드시 `textContent`로 렌더링.
- **카카오는 메인 UI에 섞지 않는다.** "결과 공유하기" 버튼(기존 패턴 재사용)만 두고, 그룹 논의/AI 처리/투표는 전부 웹 화면 안에서 끝낸다 — UIUX_DESIGN_REFERENCE.md §4의 권장 아키텍처와 동일.
