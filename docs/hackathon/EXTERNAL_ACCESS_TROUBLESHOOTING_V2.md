# 외부 접속 불가 재조사 V2 (경영진 "모든 사람이 안 된다" 반박 대응)

- 조사일: 2026-09-23 (V1 `EXTERNAL_ACCESS_TROUBLESHOOTING.md`의 보강 문서, 대체 아님)
- 방식: 온라인 커뮤니티/포럼 검색 + 서버 읽기 전용 재확인. **코드·서버 설정 변경 없음, `.env` 미열람, git 커밋·푸시 없음.**
- V1과의 관계: V1의 핵심 결론("서버 정상, 원인은 접속자 측 환경일 가능성")은 **틀리지 않았다.**
  이번 재조사에서 그 결론을 뒤집는 증거는 나오지 않았고, 오히려 강화됐다.
  다만 V1의 표현("접속자 측 네트워크가 원인일 것")이 경영진의 인식("모든 사람이 안 된다")과 충돌하는 이유를
  이번 문서에서 설명한다: **"모든 사람"이 아니라 "경영진 주변의 특정 조건을 공유하는 사람들"이 안 되는 것(추정)** 으로 보인다.

## 0. 새로 발견한 것 (TL;DR)

1. **"아무도 못 들어온다"는 사실이 아니다.** 서버 로그(`sudo docker logs agt001-backend-1 --tail 500` 실측)에
   최소 4~5개의 서로 다른 외부 IP에서 `GET /room.html → POST /room → POST /chat → polling` 전체 플로우가
   HTTP 200으로 성공한 기록이 있다 (아래 §1 표 참고). 서버가 완전히 막혀 있으면 나올 수 없는 기록이다.
2. **신규 실패 흔적 2종을 로그에서 확인 (둘 다 "연결 자체 불가"가 아님):**
   - `https://` 오시도 흔적: 2개 IP에서 평문 HTTP 포트(8643)에 TLS 핸드셰이크 바이트(`\x16\x03\x01…`)를 보내
     `400 Bad request version` 발생 (총 14건 중 12건). 즉 누군가 `https://144.24.91.250:8643/...`으로 접속 시도(추정:
     브라우저 자동 업그레이드 또는 사용자가 `https://`로 입력). 브라우저 화면에는 "연결 실패"처럼 보인다.
   - URL 추측 흔적: `GET /static/room.html`, `GET /site/<id>/` 등 존재하지 않는 경로에 대한 `404` 8건.
     링크가 아닌 손타이핑/추측 입력이 있었다는 정황(추정).
3. **진짜 네트워크 차단(사내 방화벽 타임아웃)은 서버 로그에 안 남는다.** V1에서 빠진 설명이다:
   클라이언트 측 아웃바운드 차단으로 SYN이 서버에 닿지 않으면 서버 로그에는 아무 기록도 없다.
   그래서 "로그에 실패가 안 보인다 = 실패가 없다"가 성립하지 않으며, 반대로 "로그에 성공이 있다 = 일부는 된다"만 성립한다.
   이 비대칭이 모순("로그는 성공, 경영진은 실패")의 정체다.
4. **온라인 커뮤니티 재검색 결과, "일부는 되고 일부는 안 되는" 패턴의 가장 설득력 있는 설명은
   회사/기관망 vs 개인 모바일망 차이**이다 (아래 §2). 통신사별 차별 처리·sslip.io 통신사 차단의 직접 사례는 찾지 못했다.
5. **카카오톡 인앱 브라우저는 "연결 불가"의 주범이라는 직접 증거를 찾지 못했다** (V1 판단 유지).
   대신 "열리긴 열리는데 깨져 보인다 → 사용자가 '안 된다'고 보고" 계열의 2차 리스크라는 V1 분류가
   추가 검색(데브톡 흰화면 민원 다수, Android 인앱 종료 시 캐시 삭제, Blob 다운로드 차단, 쿠키 제한 환경 CSRF 오류)으로도 유지된다.
   이전 세션에서 실측했다는 "인앱이 링크를 `data:` URL로 렌더링 → localStorage/crypto 오류" 패턴에 대한
   **외부 독립 사례는 이번 검색에서 확인하지 못했다(추정 등급 유지).**

### 1-3. 로그 해석의 비대칭 (V1에서 빠진 점 — 이번 문서에서 보강)

- **서버 로그에 성공이 있으면 "된다는 사람"이 실재함이 확정**된다 (위조 불가에 가까움).
- **서버 로그에 실패가 없다고 "안 된다는 사람"이 거짓이 되지는 않는다.**
  클라이언트 측 아웃바운드 차단(사내 방화벽·프록시)은 패킷이 서버에 닿기 전에 버려지므로 서버 로그에 흔적이 남지 않는다.
  즉 이번 로그는 "모든 사람이 안 된다"를 반박하지만, "특정 환경의 사람이 안 된다"와는 양립한다.
- 결론: **"서버가 완전히 막혀서 아무도 못 들어온다"는 가설은 기각. "환경이 맞는 사람은 되고, 안 맞는 사람은 안 된다"가 유력(추정).**

## 2. "일부는 되고 일부는 안 되는" 패턴 — 온라인 커뮤니티 재검색

V1도 읽고 같은 가설을 재검증했다. 결론부터: **V1 Top 3의 순위는 유지**한다.
이번에 새로 추가된 것은 (a) "사내망 vs 모바일망" 가설을 뒷받침하는 국내·외 커뮤니티 증언 추가 확보,
(b) 카카오톡 `data:` URL 가설의 외부 확증 실패를 명시한 것, (c) 로그의 `https://` 오시도라는 새 물증과 HTTP 경고 이슈의 연결이다.

### 2-1. 회사/기관 네트워크 vs 개인 휴대폰 네트워크 (가장 유력 — V1 순위 1위 유지·증거 보강)

- ServerFault ("Is it safe to serve HTTP/HTTPS over ports 8080/8443", 50k 조회):
  비표준 포트 사이트를 운영한 답변자가 **"우리 방문자의 약 50%가 접속 불가였고, 상대 IT와 방화벽 허용 규칙을 협의해야 했다"** 고 증언.
  기업망 기본값이 `deny all; allow 80; allow 443; …` 형태라 비표준 포트가 막히는 것이 정설이라는 취지.
  → "일부는 되고 일부는 안 된다"의 교과서적 패턴.
- 국내 SharedIT 방화벽 아웃바운드 스레드: 실무자들이 "사용자 대역 인터넷 방화벽은 http·https 2개만 열어도 인터넷 사용에 무리 없음",
  "내부→외부는 웹포트만 열고 하나씩 추가" 같은 구성을 당연하게 논의. 즉 **국내 기업망에서도 8643 같은 포트 아웃바운드가 막혀 있는 것이 이상하지 않다**(추정: 일반론).
- Palo Alto LIVEcommunity (카카오톡 앱 이슈, 2025-08): 한국 사용자가 **회사 wifi에서는 카카오톡 로그인 오류(50101), 개인 핫스팟에서는 정상**이라는
  보고. 카카오 관련 트래픽이 기업망에서 다르게 처리되는 실측 사례로, "사내망은 안 되고 개인망은 된다" 패턴의 실존을 보여준다.
- Cisco 커뮤니티 IronPort 사례: 비표준 포트(44444) 앱이 프록시 설정(`HTTP connect ports`) 문제로 일부 환경에서만 안 되는 증언.
  기업 프록시가 비표준 포트를 별도 허용 목록으로 관리한다는 방증.
- 우리 로그와의 정합성: 성공 IP들은 모바일/가정망에서 직접 URL로 들어온 사용자처럼 보이고(추정),
  경영진 주변(같은 사무실·같은 wifi 공유 추정)은 정확히 막히는 쪽에 걸렸을 수 있다(추정).
  **판별법은 V1과 동일: 안 된다는 사람에게 모바일 데이터망(와이파이 끄고)으로 재시도 요청.**

### 2-2. 카카오톡 공유 링크 vs 직접 URL 입력 (V1 판단 유지: 2차 리스크, 주범 아님)

- 카카오 데브톡 실측 답변(공식): **Android 인앱브라우저는 웹뷰 종료 시 캐시를 삭제**하므로 항상 최초 접근처럼 느리게 동작.
  "아이폰은 빠르고 안드로이드는 3~5초" 같은 기종별 체감 차이가 보고됨. "안 된다"가 아니라 "느리다/이상하다" 계열.
- 데브톡 민원 다수: "React + tailwind 앱이 Android + 카톡 인앱에서만 흰화면", "알림톡 링크 타고 빈화면",
  "인앱에서만 영상 다운로드 불가(Blob 생성 차단 — 보안·메모리 정책)", 쿠키 제한 환경에서 CSRF 토큰 검증 실패(Kakao Developers 트러블슈팅 공식 문서).
  → 즉 **인앱은 "연결은 되는데 앱이 깨진다"는 형태로 사용자의 "안 된다" 보고를 만들 수 있다.**
- **외부 확증 실패 (명시):** 이전 세션 실측이라는 "카톡 인앱이 링크를 `data:` URL로 렌더링해서 localStorage/crypto 오류" 패턴을
  설명·확증하는 외부 커뮤니티 글은 이번 검색(Reddit·데브톡·Stack Overflow 계열·국내 블로그)에서는 찾지 못했다.
  관련어(`data:` URL·localStorage·WebView) 검색 결과는 Cordova InAppBrowser·Blob 정책 등 인접 주제뿐이었다.
  따라서 이 가설은 **"우리 환경에서 실측된 1차 관측" 상태로 두고, 일반론처럼 주장하지 말 것 (추정).**
- 카카오 공유 특유의 변수 1개 추가 (추정): Kakao Developers 트러블슈팅은 "공유 메시지의 이미지 URL이 외부에서 접근 불가면
  카카오 스크래핑 서버가 실패"한다고 명시한다. 우리 케이스는 이미지 공유가 아니라 링크 접속이라 직접 해당하지 않지만,
  **"카톡으로 받은 링크"가 발신자의 입력 변형(https 오기입·줄바꿈·미리보기 캐시)과 결합될 여지**는 있다(추정).

### 2-3. 특정 통신사(SKT/KT/LG U+)의 비표준 포트 차별 처리 (직접 사례 없음 — 추정)

- 이번 검색에서 **한국 이동통신사가 아웃바운드 비표준 포트를 차단한다는 직접 사례는 찾지 못했다.**
  찾은 것은 반대 방향(인바운드·공유기 포트포워딩: LG U+ 사설IP/NAT 이중화, 백메가·아정당 글)과 기업용 방화벽 상품 소개뿐이다.
- 성공 로그의 IP들이 한국 통신사 대역으로 추정되는 점과-community 사례 부재를 종합하면,
  "통신사 A는 되고 B는 안 된다" 가설은 **현시점 증거 부족(추정)** 으로 판단한다.
  통신사 문제는 질문 목록에는 남기되(어느 통신사·와이파이인지), 주 용의자로 올리지 않는다.

### 2-4. iOS Safari vs Android Chrome vs 카톡 인앱의 HTTP(비HTTPS) 처리 차이 (V1 순위 2위 유지 + 로그 물증 추가)

- BleepingComputer (Google 공식 발표 인용, 2025-10-30): Chrome은 **147(2026-04, Enhanced Safe Browsing 10억+ 사용자) →
  154(2026-10, 전체 기본값)** 일정으로 "Always Use Secure Connections"(HTTPS-First)를 기본값화.
  조사 시점(2026-09-23)은 그 사이. 즉 상대방 Chrome이 경고·확인 페이지를 먼저 띄웠을 수 있다는 V1 판단은 유효하고,
  이번에는 **로그의 `https://` 오시도 400 (12건, 2개 IP)이라는 물증**이 추가됐다:
  누군가 실제로 `https://…:8643`으로 접속을 시도했고, 우리 서버는 평문 HTTP라 400을 반환했다.
  사용자 화면에는 "연결되지 않음"처럼 보인다(추정).
- Apple 공식 지원 문서: Safari는 HTTP 사이트에 "Not Secure" 경고를 표시(차단은 아님).
  iOS 26의 Fingerprinting Protection 기본값화 등 Safari 강화 흐름은 있으나 **평문 HTTP 접속 자체를 막는다는 증거는 없다.**
- OS별 차이는 대체로 "경고 페이지를 보고 포기" vs "https로 오입력" 수준의 차이이지,
  "iOS는 되고 Android는 안 된다" 같은 하드한 분기는 아니다(추정).

### 2-5. ISP 레벨 DNS 필터링이 sslip.io를 일부만 차단 (직접 사례 없음 — V1 "추정" 유지)

- sslip.io/nip.io 공식 상태: 10년 이상 운영, GCP·AWS·Azure·IBM 공식 문서 참조, 초당 2만+ 쿼리.
  서비스 자체 장애라는 가설은 이번에도 기각.
- 운영자(cunnie/sslip.io) 공개 정보: abuse 신고 대응 blocklist 운영 중(`Blocked` 카운터·"Blocked Site!" 페이지 실재).
  즉 이 대역에 악용 신고가 실재하므로 **기업·공공 DNS 필터가 와일드카드 DNS를 "untrusted indicator"로 분류·차단할 여지**는 V1대로 남는다(추정).
- **"우리 통신사/회사망에서 sslip.io가 막혔다"는 직접 사례는 이번 검색에서도 찾지 못했다.**
  V1의 판별법(IP 직접 주소 vs sslip.io 도메인 분리 테스트)은 그대로 유효하므로 질문 목록에 유지한다.

## 3. 결론: "모든 사람이 안 된다"는 사실인가?

- **아니다.** 서버 로그에 서로 다른 외부 IP 최소 4~5곳의 전체 플로우 200 성공이 있다.
  "서버가 완전히 막혀서 아무도 못 들어온다"는 가설은 **기각**한다 (V1의 "서버 정상" 결론은 맞았다).
- **대신 이렇게 좁혀진다 (추정):** "직접 URL을 휴대폰 데이터망·외부망에서 연 사람은 되고,
  경영진 주변의 특정 조건(사내 wifi·`https://` 오입력·카톡 인앱 렌더링·sslip.io 도메인 사용 중 하나 이상)을 공유하는 사람은 안 된다."
- 경영진 인식과의 충돌 원인 (추정): 경영진이 확인한 "모든 사람"이 실제로는 **같은 사무실·같은 wifi·같은 전달 경로(카톡 링크)·같은 기종**으로
  편향된 표본이었을 가능성이 크다. 로그의 성공 사용자들은 그 표본 밖에 있다.
- V1이 틀린 점 1가지 (명시): V1 §5는 카톡 인앱을 "연결 불가와 무관"하다고만 했는데,
  "인앱 렌더링 깨짐 → 사용자가 '접속 안 됨'으로 보고"라는 **보고 경로**까지 포함해야 오해가 없다. 이번 문서로 보강한다.
  나머지 V1 결론(포트 차단 1순위·HTTP 경고 2순위·sslip.io 추정 3순위)은 유지한다.

## 4. 경영진에게 물어봐야 할 질문 목록 (증상 분리용 — 그대로 전달 가능)

> 목표: "안 된다"를 (a) 연결 불가(타임아웃) vs (b) 경고 페이지 vs (c) 깨진 화면 으로 분리하고,
> V1 판별법(IP vs 도메인·사내망 vs 모바일망·카톡 vs 직접입력)을 한 번에 적용한다.

1. **안 된다고 하신 분이 링크를 어떻게 여셨나요 — 카카오톡 채팅방의 링크를 눌러서 들어가셨나요, 아니면 URL을 브라우저 주소창에 직접 입력/붙여넣기 하셨나요?**
   (카톡 인앱 vs 외부 브라우저 분리. 카톡이면 "… > 다른 브라우저로 열기"로 재시도 요청)
2. **그때 네트워크가 무엇이었나요 — 회사 와이파이였나요, 집 와이파이였나요, 휴대폰 모바일 데이터(LTE/5G, 와이파이 끄고)였나요?**
   (사내망 차단 가설의 결정적 분기. 와이파이를 끄고 모바일 데이터로 같은 URL 재시도 요청)
3. **브라우저에 뜬 화면이 정확히 무엇이었나요 — ① 계속 돌다 "연결 시간 초과", ② "안전하지 않음/Not Secure" 경고, ③ 흰 화면/깨진 화면, ④ "연결이 거부됨/차단됨" 중 어느 하나인가요?**
   (①=포트·방화벽 차단, ②=`https`·HTTP 정책, ③=인앱 렌더링, ④=프록시 차단 — 추정 매핑)
4. **입력한 주소가 `http://`였나요 `https://`였나요? 주소 뒤에 `:8643`이 붙어 있었나요?**
   (로그에 `https://` 오시도 400이 실재. `https://…:8643`이면 평문 서버라 무조건 실패)
5. **`http://144.24.91.250:8643` (IP 직접)과 `http://144.24.91.250.sslip.io:8643` (도메인) 중 어느 것이 안 됐나요, 아니면 둘 다인가요?**
   (IP만 되면 DNS 문제 확정, 둘 다 안 되면 포트/HTTP 문제로 좁혀짐 — V1 판별법)
6. **휴대폰 기종·브라우저가 무엇이었나요 — 아이폰 Safari / 안드로이드 Chrome / 카카오톡 인앱 중 어느 것인가요?**
   (인앱·기종별 렌더링 차이 분리)
7. **안 된다고 하신 분들이 같은 장소(같은 사무실·같은 와이파이)에 계셨나요? 다른 장소·다른 통신사(SKT/KT/LG U+)에서 시도한 분도 계신가요?**
   (표본 편향 확인. 성공 로그는 서로 다른 대역에서 나왔음)
8. **(가능하면) 실패 화면의 스크린샷 또는 화면에 뜬 문구를 그대로 전달받을 수 있을까요?**
   ("안 된다"는 구두 보고보다 에러 문구 1장이 원인 분류에 결정적)
