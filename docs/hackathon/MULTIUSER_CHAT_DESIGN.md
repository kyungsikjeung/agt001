## 0. 결론 (먼저 읽기)

### 0.1 사용자 요구사항의 해석

사용자가 말한 "카카오톡을 통해서 여러 명이 하나의 채팅창을 같이 보면서 요구사항을 함께 도출"은
말 그대로 들으면 한 가지처럼 보이지만, 카카오 생태계의 실제 상품 구조에 비춰보면
서로 다른 3가지 해석으로 갈라진다. 각 해석의 기술적 실현 가능성을 먼저 정리한다.

| 해석 | 내용 | 실현 가능성 (5일 마감 기준) |
|---|---|---|
| **해석 A. 카카오톡 그룹채팅방 안에 우리 AI 봇이 들어간다** | 카카오톡 그룹채팅/오픈채팅방에 챗봇을 초대하고, 참여자들과 AI가 카톡 안에서 직접 대화 | **불가능 (무리)** — 카카오가 제3자 봇의 그룹채팅방 참여를 허용하는 공개 API가 없다 (§1.2). 비공식 프로토콜(LOCO) 방식은 계정 정지 리스크가 있어 해커톤 산출물에 쓸 수 없다 (추정 아님 — 공식 문서에 해당 API가 존재하지 않음이 확인됨). 단, 카카오 자체가 2026년 카톡 채팅방 내 "@ChatGPT 호출" 기능을 출시했으나 이는 카카오 자사 기능이며 우리 봇을 같은 방식으로 올릴 수 있는 개방 API는 없다 (§1.5). |
| **해석 B. 카카오톡 채널(상담톡/오픈빌더) 챗봇을 여러 명이 쓴다** | 카카오톡 채널 챗봇(1:1)을 만들고 여러 고객이 각자 대화 | **부분 가능하나 요구와 불일치 + 마감 내 무리** — 채널 챗봇은 구조적으로 1:1이며(봇-채널 1:1, 사용자별 별도 채팅방), "참여자끼리 서로의 메시지가 보인다"는 요구(요구사항 2)를 만족하지 못한다. 게다가 비즈니스 채널 인증(영업일 3~5일) + 오픈빌더 라이선스(약 3일)가 필요해 9-28 마감을 넘길 가능성이 크다 (§1.3). |
| **해석 C. 우리 웹 채팅을 다인원 공유방으로 만들고, 카카오는 초대 링크 공유 용도로만 쓴다** | `static/index.html` 채팅에 room 초대 기능을 만들고, 그 링크를 기존 `Kakao.Share.sendDefault`로 카톡 친구/그룹채팅방에 뿌린다. 실제 대화는 우리 웹에서, 카톡은 "입구" 역할 | **현실적 (마감 내 가능)** — 지금 구조(세션 + 폴링 + 카카오 공유)의 연장선이며, 새 외부 승인/심사 절차가 전혀 필요 없다. |

**결론: 해석 C로 진행하는 것을 권장한다.**
"카카오톡을 통해서"라는 표현은 해석 C에서도 성립한다 — 사용자가 카톡에서 링크를 받고,
카톡 그룹채팅방에서 "이 링크로 모여서 얘기하자"고 조율한 뒤, 실제 요구사항 도출 대화는
공유 웹 채팅방에서 AI와 함께 진행되기 때문이다. 데모 시나리오상으로도
"카톡 그룹방에 링크가 오고, 여러 명이 들어와 AI와 함께 요구사항을 정한다"는 흐름이 그대로 시연된다.

### 0.2 범위 구분 (마감 2026-09-28 기준)

**현실적으로 가능한 범위 (해석 C, 예상 작업량 1~2일):**

1. `room_id` 기반 공유방: `SESSIONS[session_id]` 1:1 구조에 `rooms[room_id]` 레이어 추가,
   메시지에 `sender` 필드 추가 (발신자 표시).
2. 초대 링크 + 카카오 공유: `?room=<room_id>` URL을 기존 `Kakao.Share.sendDefault`로 공유
   (현재 DONE/시안 시점 공유 버튼과 같은 패턴 재사용, §3.5).
3. 기존 4초 폴링 확장: 메시지 목록 전체를 내려주는 `GET /room/<room_id>/messages` +
   `since` 파라미터 정도면 충분. WebSocket/SSE 도입 불필요 (§3.3).
4. AI 상태 브로드캐스트: `room.status = IDLE | AI_THINKING | RAG_SEARCHING | GENERATING`
   같은 단일 필드를 폴링 응답에 포함해 참여자 전원에게 "AI가 생각 중" 표시 (§3.4).
5. 승인 게이트 최소 합의: "1인 승인 → 방 전체 진행"은 유지하되, **승인/거절 투표 현황을
   방 전원에게 보여주고, 승인 조건을 '참여자 N명 중 과반' 같은 단순 규칙**으로 두는
   최소 구현 (§4).

**무리인 범위 (마감 후 또는 별도 프로젝트):**

1. 카카오톡 그룹채팅방 안에서의 양방향 봇 (해석 A) — 공개 API 자체가 없음.
2. 카카오톡 채널/오픈빌더 챗봇 신규 개설 (해석 B) — 심사 기간이 마감을 초과.
3. 카카오워크 연동 — 별개 서비스이며 요구 맥락(고객 대면)과도 맞지 않음 (§1.4).
4. WebSocket 기반 실시간 + 메시지 충돌 해결(OT/CRDT 등) — 5일 안에 필요도 효과도 없음.
5. 참여자 인증/권한(카카오 로그인, 방장/게스트 구분) — 데모에는 닉네임 자칭으로 충분.

## 1. 조사: 카카오톡을 통한 그룹 대화가 기술적으로 가능한 범위

> 조사 방법: Kakao Developers 공식 문서(kakaotalk-share, kakaotalk-message, kakaotalk-channel),
> 카카오 비즈니스(상담톡/채널 챗봇) 안내, 카카오 데브톡 포럼 사례, 2026년 카톡 내 AI 호출 출시 기사를
> 웹 검색으로 확인 (2026-09-23 기준). 카카오 내부 비공개 사양은 확인할 수 없으므로 해당 부분은 "추정" 표기.

### 1.1 현재 우리 리포의 카카오 연동 상태 (실측)

- `static/index.html:41-80` — `Kakao.Share.sendDefault` (feed 템플릿) 1회성 링크 공유만 존재.
  공유 대상 선택(친구/채팅방 목록, 사용자 선택)은 카카오톡 앱이 담당하고,
  우리 서버는 메시지 전송 성공 여부를 직접 알 수 없다
  (전송 확인은 `serverCallbackArgs` + 공유 웹훅으로만 가능 — 현재 미구현).
- `backend.py:611-619` — `/chat` 응답에 `deploy_url` / `design_url` / `design_preview_url`을
  실어 내려주고, 프론트가 그 URL로 공유 버튼을 띄우는 구조.
  즉 "공유할 링크를 만들어주는 것"까지가 우리 몫이고 "누구에게 보낼지"는 카톡 앱의 몫이다.
- 양방향(카톡 메시지를 우리 서버가 받는 방향) 연동은 전혀 없다.
- 추가로 확인된 제약(추정 아님, 데브톡 실사례): `sendDefault`의 외부 링크(`webUrl/mobileWebUrl`)는
  앱 관리 페이지의 [제품 링크 관리] > [웹 도메인]에 등록된 도메인만 정상 동작하며,
  미등록 시 카드 클릭이 비활성화되는 증상이 보고되어 있다. 공유방 링크를 새 도메인(예: OCI 배포 URL)으로
  바꿀 경우 **도메인 등록 여부부터 확인할 것.**

### 1.2 해석 A — 카카오톡 그룹채팅/오픈채팅에 봇을 넣는 방식: 불가능

카카오가 공개한 메시지 발송 API는 딱 2종이며, 둘 다 "그룹방에 봇이 상주하며 대화"가 아니다.

| 상품 | 방향 | 그룹방 지원 여부 |
|---|---|---|
| 카카오톡 공유 (`Kakao.Share.sendDefault`, JS SDK) | 사용자 → 친구/채팅방, 1회성. 사용자가 카톡 앱 내 선택 화면에서 대상을 고르면 전송됨. `pickerSettings.type=chat` + `limit`로 채팅방 목록만 노출 가능하고 그룹채팅방은 최대 5개까지 선택 가능 | 링크를 그룹방에 "뿌리는" 것은 가능. 그러나 그 이후 그룹방 대화를 우리 서버가 읽거나 참여하는 기능은 없음 |
| 카카오톡 메시지 (`/v1/api/talk/friends/message/...`, REST) | 사용자 → 같은 서비스를 쓰는 친구. 수신자 `uuid`는 친구 피커/친구 목록 API로 얻어야 하며 **1회 최대 5명**, 일/월 쿼터 존재. 별도 권한 신청 필요 | 친구에게 푸시성 메시지 발송만 가능. 그룹방이라는 개념 자체가 API에 없음 |

핵심 근거:

- 그룹채팅방을 생성하거나, 기존 그룹방에 봇을 초대하거나, 그룹방 메시지를 수신하는
  공개 API는 Kakao Developers 문서에 존재하지 않는다 (확인됨).
- 카카오톡 오픈채팅에도 제3자가 임의 방에 봇으로 참여할 수 있는 개방 API가 없다 (확인됨).
- 비공식 수단으로 LOCO 프로토콜 기반 커뮤니티 SDK(예: agent-messenger.dev 문서에
  `getChats`, `sendTyping` 등 그룹/오픈채팅 조작 API가 존재)가 실재한다.
  그러나 이는 카카오 공식 API가 아니며, **정식 계정으로 사용하면 이용약관 위반·계정 정지
  리스크가 있다 (추정 — 약관 위반 여부는 카카오 정책 해석 영역).**
  해커톤 제출물 + 데모 시연용으로 의존해서는 안 된다.

### 1.3 해석 B — 카카오톡 채널/상담톡/오픈빌더 챗봇: 1:1이라 요구와 불일치 + 일정 초과

카카오의 양방향 봇 상품 구조 (공식 문서 기준):

- **카카오톡 채널 + 챗봇(오픈빌더)**: 사용자가 채널을 추가하고 채널 채팅방에서 봇과 대화.
  구조적 특성상 **사용자별 1:1 채팅방**이며, 봇-채널도 1:1 연결이다
  (한 채널에 두 봇 연결 불가, 채팅방 메뉴와 챗봇 동시 사용 불가).
  "참여자끼리 서로의 메시지가 보인다"는 요구사항 2를 이 구조로는 만족할 수 없다.
- **상담톡**: 고객이 먼저 상담을 열어야 하는 1:1 상담 상품. 그룹 대화 개념 없음.
- **스킬(Skill) API**: 챗봇 블록에서 우리 서버로 웹훅 호출 → 응답 반환. 이 부분은 우리 NIM
  파이프라인과 붙일 수는 있으나, 역시 1:1 대화 틀 안이다.
- **개설 소요시간 (추정 포함)**: 비즈니스 채널 인증 심사 영업일 3~5일 + 오픈빌더
  라이선스 신청 승인 약 3일(커뮤니티 가이드 기준, 시점별 상이 — 추정).
  순차 진행 시 9-28 마감을 넘길 가능성이 크고, 병렬로 통과된다 해도 스킬 서버 연동·검증에
  최소 1~2일이 더 든다. 즉 **해석 B는 요구 불일치 + 일정 초과**의 이중 문제.

참고로 데브톡에는 "채널 추가 직후 챗봇이 바로 동작하지 않는다", "진입 경로에 따라
채팅 화면이 2가지로 나뉜다" 같은 실운영 이슈가 보고되어 있어, 데모 안정성 측면에서도 불리하다.

### 1.4 카카오워크: 별개 서비스이므로 제외

카카오워크는 기업용 메신저(Slack 유사)로, 일반 카카오톡과는 계정·앱·API가 분리된 별개 서비스다.
우리 시나리오(외부 고객이 카톡으로 들어와 요구사항 도출)는 소비자용 카카오톡 맥락이므로
카카오워크 연동은 요구와 무관하다. 검토에서 제외한다.

### 1.5 2026년 카톡 내 "@AI 호출" 기능: 트렌드 참고용 (우리 봇 탑재 불가)

2026년 카카오는 카톡 채팅방(1:1 + 그룹 모두)에서 "@ChatGPT" 멘션으로 AI를 호출하는
자사 기능을 출시했다 (언론 보도 기준). 이는 사용자가 원하는 UX와 정확히 같은 모양이지만,
**카카오 자사(제휴) 기능이며 제3자가 자기 봇을 같은 방식으로 카톡 그룹방에 올릴 수 있는
개방 API는 확인되지 않는다 (2026-09-23 기준, 추정).**
따라서 "카카오가 이런 UX를 공식 지원한다 = 우리 데모의 공유방 UX가 낯설지 않다"는
발표 논거로는 쓸 수 있으나, 구현 수단으로는 쓸 수 없다.

### 1.6 조사 결론

> **우리 웹 채팅에 "여러 명 초대" 기능을 만들고, 카카오톡은 그 링크를 공유하는
> 용도로만 쓰는 것(해석 C)이 유일하게 마감 내 가능한 정답이다.**
> 해석 A는 API 부재, 해석 B는 구조 불일치 + 심사 기간 초과, 카카오워크는 논외다.

## 2. 현행 아키텍처 분석 (공유방 설계의 출발점)

### 2.1 세션 구조: 1:1 전제의 구체적 위치

`backend.py`의 상태 저장소는 아래 세 가지가 한 덩어리로 묶여 있다.

```
SESSIONS[session_id] = {
  "state": GREETING | GATHERING | AWAIT_APPROVAL | QUOTED | GENERATING | DONE,
  "requirement_id": <8자리>,
  "last_request": <원문>,
  "quote": {...}, "design_url": ..., "codegen": {...}, ...
}
```

1:1 전제가 박혀 있는 지점 (파일:줄 기준):

- `backend.py:516-520` — `session_id` 없으면 신규 발급 + `setdefault`로 세션 생성.
  호출자 식별이 전혀 없어서 "누가 말했는지"를 구분할 수 없다.
- `backend.py:522-609` — 상태머신 전체가 단일 화자의 턴테이킹을 가정.
  특히 `GENERATING` 분기(`524-550`)는 폴링 요청의 `message` 본문을 무시하고 진행상황만 보는데
  (`Math.random()` 난수 메시지 — `static/index.html:99`),
  다인원 구조에서도 이 "본문 무시" 규칙이 그대로 재사용 가능하다 (§3.3).
- `SESSIONS`는 인메모리 dict + `SESSIONS_LOCK` + `generated/sessions.json` 원자 저장
  (`save_sessions:40-50`, `load_sessions:53-72`). 재시작 시 `GENERATING → QUOTED`로
  되돌리는 복구 규칙이 이미 있다 — 공유방도 이 규칙을 그대로 승계하면 된다.
- `contracts/gate_to_quote.schema.json` — `customer_id`가 단일 값 필드.
  다인원 합의 시 "누가 승인했는지" 목록이 필요해지면 이 스키마(와 BND-1) 개정이 필요하다 (§4).

### 2.2 프론트 구조: 단일 페이지 + 발신자 구분 없음 + 4초 폴링

- `static/index.html:47-57` — `sessionId` 전역 1개, `addMsg(text, who)`는 `user/bot` 2종만 구분.
  다인원 표시에는 `sender` 이름 라벨 + 본인/타인 색 구분이 추가되어야 한다 (§3.2).
- `static/index.html:93-113` — `GENERATING` 동안 4초 간격 폴링, 상태가 바뀌면 중단하고
  결과를 렌더링. 폴링 요청이 `message: 난수`를 보내 세션을 오염시킬 가능성이 있다는 지적이
  EFFICIENCY_PLAN §1-⑥에 이미 있으나, `GENERATING` 분기가 본문을 무시하므로 기능상 무해함이 확인됨.
  공유방 폴링도 같은 패턴을 쓰되, 난수 대신 빈 메시지 + `poll=1` 구분을 명시화하는 것을 권장 (§3.3).
- `static/index.html:59-80` — 카카오 공유 버튼 생성기는 URL + 옵션만 받으므로,
  공유방 초대 링크(`?room=...`)에도 그대로 재사용 가능하다 (§3.5).

### 2.3 AI 처리 과정 노출: 현재는 "GENERATING 고정문" 1단계뿐

현재 참여자(1인)에게 보이는 AI 상태는 사실상 2가지뿐이다.

| 구간 | 현재 노출 | 비고 |
|---|---|---|
| RAG 검색 (`rag_precheck`) | 노출 없음 — `/chat` 응답이 올 때까지 무응답 대기 | NIM 동기 호출이라 체감 지연 발생 (EFFICIENCY_PLAN §1-①에서 타임아웃 25초로 완화済) |
| 견적 (`build_quote`) | 노출 없음 — 동일하게 대기 | 실패 시 정적 폴백으로 500 방지済 (STATUS.md 효율화 Top 2) |
| 코드생성 (`GENERATING`) | "코드 생성 중입니다... 잠시만 기다려주세요." 고정문 + 4초 폴링 | 단계 구분 없음 |

즉 요구사항 4("AI가 응답 생성 중인지, RAG 검색 중인지")는 **현재 1:1에서도 미구현**이며,
공유방 설계와 함께 "상태 필드 1개 추가" 형태로 해결하는 것이 가장 싸다 (§3.4).

## 3. 설계: 웹 채팅 다인원 공유 세션

### 3.1 데이터 모델: `session_id`(1인) → `room_id`(N인)

최소 변경 원칙: 기존 1:1 세션 상태머신을 건드리지 않고, 그 위에 방(room) 레이어를 얹는다.
`SESSIONS` dict와 파일 백업(`sessions.json`) 구조는 유지하고, 방이 세션을 감싸는 형태다.

```
rooms[room_id] = {
  "room_id": str,                 # 초대 링크에 들어가는 ID (?room=<room_id>)
  "session_id": str,              # 기존 SESSIONS 키 재사용 — 상태머신은 그대로 1개
  "created_at": str,
  "members": [                    # 닉네임 자칭식 (인증 없음 — §3.6)
    {"member_id": str, "nickname": str, "joined_at": str, "last_seen": str}
  ],
  "messages": [                   # 방 전체 대화 로그 (그룹채팅처럼 전원에게 동일하게 노출)
    {"seq": int, "member_id": str | "ai",
     "nickname": str,             # AI면 "AI 어시스턴트" 고정
     "text": str, "ts": str,
     "kind": "chat" | "ai_reply" | "system" | "vote"}
  ],
  "ai_status": "IDLE" | "RAG_SEARCHING" | "THINKING" | "QUOTING" | "GENERATING" | "DONE",
  "votes": {                      # §4 승인 투표 현황
    "<member_id>": "approve" | "reject"
  }
}
```

설계 결정 (이유 포함):

1. **방당 상태머신 1개 유지** — `SESSIONS[session_id]`의 `state` 전이 로직
   (`GREETING → ... → DONE`)을 N개로 복제하지 않는다. 방 참여자 N명의 발화는 모두
   같은 상태머신의 입력으로 들어가고, AI 응답 1개가 방 전체에 브로드캐스트된다.
   이렇게 해야 승인 게이트(⑦)의 "단일 확정안"语意이 깨지지 않는다.
2. **메시지 로그는 방이 소유** — 현재 프론트는 새로고침하면 대화가 날아간다
   (서버에 대화 로그가 없고 `reply` 단발 응답만 있음). 공유방에서는 "늦게 들어온 사람도
   이전 대화를 볼 수 있어야 한다"는 요구가 생기므로, `messages[]` append-only 로그가 필수다.
   기존 1:1 응답(`reply`)은 `kind=ai_reply` 메시지로 그대로 쌓으면 된다.
3. **파일 백업 승계** — `save_sessions()`가 SESSIONS 전체를 직렬화하듯,
   `rooms`도 같은 `sessions.json` (또는 `rooms.json` 분리 — 추정 아님, 선택 사항)에
   같은 원자 저장(tmp+rename)으로 얹는다. `GENERATING → QUOTED` 복구 규칙도 방 단위로 동일 적용.
4. **BND 스키마 영향**: BND-1의 `customer_id` 단일 필드는 방 구조와 충돌한다.
   최소 개정안은 `customer_id` 유지 + `room_id`, `approved_by: [...]` 추가
   (additionalProperties가 true이므로 하위 호환으로 추가 가능 — §4).

### 3.2 여러 참여자 메시지 구분 (발신자 표시)

백엔드: `/chat` 요청에 `member_id` + `nickname`을 받고, 저장되는 모든 메시지에
`sender`를 기록한다. AI 응답(`reply`)도 `sender="ai"` 메시지로 로그에 추가한다.

프론트(`static/index.html`의 `addMsg` 확장, 개념 스케치 — 코드 수정 아님):

- 메시지 버블에 **닉네임 라벨 1줄 추가** (AI는 "🤖 AI 어시스턴트" 고정, 시스템 메시지는 중앙 회색).
- 본인 메시지는 우측 정렬(기존 `.user`), 타인 메시지는 좌측 정렬 + 닉네임 색상 구분
  (기존 `.bot` 스타일 재사용 + 닉네임별 hue 해시 — 구현 수십 줄 수준).
- 입장 시 `prompt()` 수준의 닉네임 입력이면 데모에 충분하다 (인증은 무리 범위, §0.2).
- 투표 메시지(`kind=vote`, "○○님이 승인했습니다 (2/3)")는 시스템 메시지로 렌더링해
  합의 진행상황을 방 전원이 보게 한다 (§4 연계).

### 3.3 실시간 갱신: 4초 폴링 확장을 권장 (WebSocket/SSE 도입 반대)

**권장: 현재 4초 폴링을 그대로 확장한다.** 이유는 아래 비교표와 같다.

| 방식 | 장점 | 단점 (5일 마감 기준) |
|---|---|---|
| **폴링 확장 (권장)** | 구현 반나절. 기존 `startPolling` + `GENERATING` 분기 패턴 재사용. `messages` 전체 또는 `since` 증분 조회 1개 엔드포인트(`GET /room/<id>/messages?since=<seq>`) 추가면 끝. 서버 상태 비저장이라 Render 무료 티어(콜드스타트, 프로세스 재시작)에서도 안전. 동시 N명 폴링 부하도 데모 규모(방당 3~5명 × 4초)에서는 무시 가능 | 4초 지연. 타이핑 인디케이터 같은 sub초 실시간은 불가 — 그러나 요구사항 도출 대화에 불필요 |
| SSE | 서버→클라이언트 푸시로 지연 단축 | Flask `threaded=True`에서 장시간 연결이 스레드 점유. Render 무료 티어의 요청 타임아웃·프록시 버퍼링과 상성 문제 (추정 — 환경별 상이). 구현·검증에 최소 반나절~1일 추가 |
| WebSocket | 양방향 실시간 | `flask-socketio`/gevent 등 의존성 추가 + `Dockerfile.backend` 재빌드 (EFFICIENCY_PLAN §2-②③의 "마감까지 Dockerfile 동결" 원칙과 정면 충돌). 세션 백업·OCI 배포 검증까지 하면 1~2일 소모. 과잉 스펙 |

폴링 확장 시의 오염 방지: 현재 `message: 난수` 패턴(EFFICIENCY_PLAN §1-⑥ 지적)은
공유방에서 그대로 쓰면 **난수 메시지가 방 로그에 쌓이는** 실제 오염이 된다.
따라서 공유방 폴링은 메시지 전송과 조회를 분리한다:

- 전송: `POST /room/<id>/chat {member_id, message}` — `message` 비어 있으면 상태 조회만.
- 조회: `GET /room/<id>/messages?since=<seq>` — `messages[since:]` + `ai_status` 반환.
- 기존 1:1 `/chat` + 난수 폴링은 건드리지 않는다 (하위 호환).

### 3.4 AI "생각 중" 표시: `ai_status` 단일 필드 브로드캐스트

`rooms[room_id].ai_status` 1개 필드를 폴링 응답에 항상 포함하고, 프론트는 값에 따라
상단 상태바 1줄을 갱신한다. 상태 전이는 기존 동기 호출 지점에 **대입 1줄씩**이면 된다.

| `ai_status` 값 | 설정 시점 (기존 코드 위치) | 프론트 표시 예시 |
|---|---|---|
| `IDLE` | 평상시, `DONE` 후 | (상태바 숨김) |
| `RAG_SEARCHING` | `rag_precheck()` 호출 직전 | "🔍 과거 프로젝트를 검색 중..." |
| `THINKING` | NIM chat 호출 직전 (`call_nim` 전) | "🤖 AI가 답변을 생각 중..." |
| `QUOTING` | `build_quote()` 진입 시 | "🧾 견적을 계산 중..." |
| `GENERATING` | 기존 `GENERATING` 상태와 1:1 대응 | "코드 생성 중입니다... (최대 90초)" (기존 문구 유지) |
| `DONE` | 기존 `DONE` 전이 시 | "✅ 완료" |

주의: 현재 RAG/견적은 요청 스레드에서 동기 blocking이라, 상태를 먼저 저장하고
`save_sessions()` 후 긴 작업을 시작하는 순서로 두어야 폴링하는 타인이 중간 상태를 볼 수 있다.
(지금 구조는 응답이 올 때까지 상태가 안 보이므로, 상태 선기록이 핵심이다.)
코드생성처럼 백그라운드 스레드면 자연스럽게 보인다.

### 3.5 카카오톡 연동: 초대 링크 공유 (기존 버튼 재사용)

흐름 (데모 시나리오 그대로):

1. 방 생성자가 웹 채팅에서 "공유방 만들기" → `room_id` 발급 → 초대 URL
   (`https://<배포호스트>/?room=<room_id>`) 생성.
2. 기존 `addKakaoShareButton(url, opts)`에 이 URL을 넘겨 `Kakao.Share.sendDefault` 실행.
   사용자는 카톡 앱 내 선택 화면에서 친구 또는 **그룹채팅방(최대 5곳)**을 골라 전송
   (공식 문서의 `pickerSettings` 사양).
3. 초대받은 사람은 카톡에서 링크를 눌러 웹 채팅방에 입장 → 닉네임 입력 → 즉시 전체 로그 열람.
4. 이후 요구사항 도출·승인 투표·견적·시안 확인까지 전부 공유방에서 진행.
   시안(`design_url`)/배포(`deploy_url`) 링크도 같은 방에 `ai_reply` 메시지로 쌓이므로,
   방 참여자는 카톡으로 다시 공유하지 않아도 된다 (물론 같은 공유 버튼으로 카톡에 뿌릴 수도 있음).

구현 체크리스트 (공유 버튼 관련):

- [ ] 배포 호스트 도메인이 카카오 앱의 [제품 링크 관리] > [웹 도메인]에 등록되어 있는지 확인
  (미등록 시 카드 링크 비활성화 실사례 — §1.1).
- [ ] 초대 링크에 `serverCallbackArgs: {room_id}`를 붙이면 공유 웹훅으로 "어느 방 초대가
  실제로 카톡에 전송됐는지"를 서버에서 확인할 수 있다 (선택 사항, 마감 후).
- [ ] 카카오 메시지 발송 API(REST, 친구 최대 5명)는 **쓰지 않는다** — 권한 신청 + 친구 피커 UI
  구현이 필요하고, 공유(SendDefault)만으로 초대 목적은 달성되므로 과잉이다.

### 3.6 인증·보안·악용 방지 (최소선)

- 데모 범위: 닉네임 자칭 + `member_id`는 입장 시 `uuid` 발급 후 `localStorage` 보관.
  방 폭파·추방 기능 없음. 초대 링크를 아는 사람은 누구나 입장 (오픈채팅 유사 모델).
- `requirement_id`/`room_id` 새니타이즈는 기존 `_sanitize_requirement_id` 패턴 재사용
  (영숫자/하이픈/언더스코어).
- 메시지 길이 상한 (예: 2000자) — 무한 폴링 로그 폭증 방지 + 프롬프트 인젝션 표면 축소
  (`_sanitize_spec`와 같은 철학).
- XSS: 기존 프론트는 `textContent` 사용으로 안전 (`static/index.html:54`) — 닉네임도
  반드시 `textContent`로 렌더링할 것.
- 정식 인증(카카오 로그인 등)은 무리 범위 — 마감 후 과제.

## 4. 설계: 다인원 합의 승인 게이트 (⑦ 확장)

### 4.1 문제 정의

현재 `AWAIT_APPROVAL` 분기(`backend.py:566-576`)는 **먼저 말한 1명의 "승인/거절" 한 마디**로
방 전체의 운명이 결정된다. 공유방에서 그대로 두면:

- A가 "승인"을 쳐서 견적으로 넘어갔는데 B는 반대했던 상황이 방 로그에도 합의 근거도 없이 진행됨.
- 거절 시 `GATHERING`으로 돌아가는데 "누가 왜 거절했는지"가 남지 않아 재논의가 어려움.

### 4.2 최소 구현 제안 (마감 내): "투표 현황 공개 + 단순 과반 규칙"

상태머신은 그대로 두고(단일 확정안 유지), 승인 조건만 바꾼다.

```
AWAIT_APPROVAL 방 로직:
- "승인"/"거절" 발화 → rooms.votes[member_id] = approve/reject 로 기록 (덮어쓰기 가능)
- kind=vote 시스템 메시지 브로드캐스트: "○○님이 승인했습니다 (찬성 2/3)"
- 판정 규칙 (단순 과반, 동점은 미결 유지):
  - 찬성 > 참여자/2  → 기존 승인 경로 (build_quote → QUOTED)
  - 반대 > 참여자/2  → 기존 거절 경로 (GATHERING + 사유 요청)
  - 그 외             → 대기 ("○○님의 의견을 기다리고 있습니다")
```

이 설계가 "최소"인 이유:

- `backend.py:567-574`의 승인/거절 본체(`build_quote`, 상태 전이)는 한 줄도 안 바뀐다.
  바뀌는 것은 "그 본체로 들어가는 조건"뿐이다.
- `votes` dict 1개 + 판정 함수 1개 + 프론트 투표 현황줄이 전부다 (예상 반나절).
- BND 스키마 개정도 하위 호환 추가(`approved_by`, `room_id`)로 충분하다:

```json
// BND-1 개정안 (기존 required 3종 유지 + 2개 추가, 모두 optional 취급)
{
  "requirement_id": "req_20260921_001",
  "confirmed_items": ["로그인", "상품목록"],
  "customer_id": "cust_방생성자 (대표 1명, 기존 필드 유지)",
  "room_id": "room_xxxx (신규, optional)",
  "approved_by": ["cust_A", "cust_B"]  // (신규, optional — 합의 근거)
}
```

### 4.3 마감 후 확장 (이번에 하지 않는다)

- 가중 투표(방생성자 거부권), 투표 기한 타이머 + 에스컬레이션(TEAM_A_SPEC §9의 G12 재사용),
  항목별 개별 승인(견적 옵션 A/B/C를 참여자별로 다르게 지지), 익명 투표.
- 이 중 어느 것도 데모("3명이 모여 승인 버튼을 눌러 통과")에는 필요 없다.

## 6. 불확실한 점 (추정 명시)

   하나이므로, 유료 플랜·타 환경에서는 재평가 가능.
4. **(추정)** 2026년 카톡 "@AI 호출"에 제3자 봇 탑재 경로가 향후 개방될 가능성 —
   2026-09-23 기준 개방 API 미확인. 카카오-OpenAI 제휴 구조상 당장 개방 가능성은 낮다고 보나,
   발표 Q&A용으로는 "플랫폼 방향성과 일치" 정도로만 언급할 것.
