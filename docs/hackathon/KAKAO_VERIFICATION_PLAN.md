# 카카오톡 연동 검증 계획 (room.html Error 4019)

> 대상: `static/room.html` "카카오톡으로 초대하기" 버튼에서 발생한 Error 4019 원인 확정 + 재발 방지.
> 원칙: 코드는 수정하지 않고 검증만 한다. 브라우저 실측은 이 문서의 절차대로 사람이 실행한다.

## 요약

- 기존 검증 상태: `static/index.html`의 카카오 공유는 실사용자 클릭 → 공유 팝업 → 실제 카톡 수신까지 검증 완료 (`docs/hackathon/ENVIRONMENT.md` §3-6, 커밋 `c510f2b`).
- 오늘의 문제(사용자 보고): 새로 만든 `static/room.html`을 **서버를 거치지 않고 `file://`로 직접 열어서** "카카오톡으로 초대하기"를 누르니 Error 4019("웹 도메인을 앱 관리 페이지의 [제품 링크 관리]에 등록해야 합니다") 발생.
- 현재 가장 유력한 가설: **`file://` 접근이 원인인 착시 버그** (추정 — 확정 아님). 근거:
  1. 카카오 데브톡 답변 실측: "`file://`에서 JS SDK를 사용했기 때문에" 4019가 발생한다는 동일 증상 사례가 있다 (조사 결과, 출처는 §6 참고).
  2. 공식 문서 규칙상 JS SDK 도메인에 `file://` 형식 등록이 가능하지만, 이 앱에는 `file://`가 등록된 기록이 없다 (`ENVIRONMENT.md` §3-6에는 `http://144.24.91.250.sslip.io:8643`만 기록).
  3. `file://`에서는 카카오 이전에 `fetch('/room')` 자체가 실패하므로 방 생성부터 안 되는 구조다 (`room.html:268`).
- 그래도 재검증이 필요한 이유: `file://` 가설이 100% 확정은 아니다. 정말로 도메인 등록이 빠져 있는 것일 수도 있고(특히 로컬 `127.0.0.1:8643`은 등록 기록 없음 — 추정), `room.html` 특유의 `?room=<id>` 공유 링크가 제품 링크 검증을 타는 것일 수도 있다.
- 이 문서의 할 일: 아래 §1→§4 체크리스트를 순서대로 실행하면 (A) `file://` 가설 확정/기각, (B) 로컬 서버 정상 동작, (C) OCI 배포본 `room.html` 정상 동작, (D) 콘솔 등록 상태까지 모두 확정된다.

## 1. 재현 가능한 검증 절차 (file:// vs 로컬 서버 vs OCI)

> 목표: "4019의 원인이 `file://`인지, 도메인 미등록인지"를 대조 실험으로 확정한다.
> 공통 준비물: Chrome(또는 Edge) + 개발자도구(F12) + 카카오톡 수신 확인할 휴대폰. 팝업 차단을 끄지 말고 기본값으로 둔다(실사용자 조건 재현).

### 1-0. 공통 확인 방법 (모든 시나리오에서 동일하게 수행)

- [ ] 1-0a. 콘솔에서 SDK 초기화 확인
  - 확인 방법: 개발자도구 Console 탭에서 실행: `window.Kakao && Kakao.isInitialized()` → `true`인지, `Kakao.VERSION` 출력.
  - 기대 결과: 서버 경유 시 `true` + `2.7.2`. `file://`에서는 SDK 스크립트 자체는 로드될 수 있으나 이후 `sendDefault`에서 4019가 나는지 본다.
- [ ] 1-0b. 에러 메시지 전문 확보
  - 확인 방법: 버튼 클릭 후 Console의 빨간색 에러를 펼쳐서 **Error 코드(4019인지), 메시지 전문, UUID**를 복사한다. 에러 화면 캡처가 아니라 텍스트(UUID 포함)를 남긴다.
  - 기대 결과: 4019라면 메시지에 `[제품 링크 관리]` 또는 `domain mismatched! caller=...` 형태가 포함된다 (추정: SDK 버전에 따라 문구가 다를 수 있음).
- [ ] 1-0c. Network 탭 확인
  - 확인 방법: Network 탭에서 `kakaocdn`/`kapi.kakao.com` 관련 요청의 상태 코드와 응답 본문을 확인한다 (추정: `sendDefault`는 팝업(`sharer`) + 내부 인증 요청을 사용하므로, 요청 자체보다 콘솔 에러 전문이 1차 판정 근거다).
  - 기대 결과: 정상 시 공유 팝업(`sharer.kakao.com` 계열 팝업 — 추정, 버전별 URL 상이 가능)이 열리고, 실패 시 콘솔에 4019 + UUID가 남는다.

### 시나리오 A. file:// 직접 열기 (문제 재현용, "실패가 정상"인 대조군)

- [ ] A-1. 재현
  - 절차: Finder/탐색기에서 `static/room.html`을 더블클릭(= 주소창이 `file:///.../static/room.html`인지 확인) → 닉네임 입력 → "카카오톡으로 초대하기" 클릭.
  - 확인 방법: 주소창 프로토콜이 `file://`임을 캡처 + §1-0a~c 수행.
  - 기대 결과: **Error 4019 발생이 정상(재현 성공)**. `caller=file://...` 취지의 도메인 불일치가 원인인 것으로 추정. 이 결과 단독으로는 "도메인 등록 누락"과 구별이 안 되므로 반드시 B·C와 비교할 것.
- [ ] A-2. 부수 확인 (왜 file://는 애초에 비교 대상이 아닌지)
  - 절차: 같은 `file://` 상태에서 방 입장/메시지 전송이 되는지 본다.
  - 확인 방법: `fetch('/room', {method:'POST'})` 계열이 Network 탭에서 실패하는지 확인.
  - 기대 결과: 방 생성·폴링부터 실패한다 (추정: `file://`에는 오리진이 없어 상대 fetch가 서버에 닿지 않음). 즉 `file://`에서의 4019는 "카카오만의 문제"가 아니라 **"서버를 안 거친 사용법" 자체가 원인**임을 보여주는 보조 증거가 된다.

### 시나리오 B. 로컬 서버 경유 (http://127.0.0.1:8643)

- [ ] B-0. 서버 기동 + 정적 서빙 확인
  - 절차: `docker compose up --build` (또는 평소 로컬 실행 방식) → `curl -i http://127.0.0.1:8643/room.html` → `curl -i http://127.0.0.1:8643/health`.
  - 확인 방법: `/room.html`이 200 + HTML로 오는지 (404면 `backend.py` 정적 서빙 문제이므로 카카오 이전에 해결할 것).
  - 기대 결과: 둘 다 200. (`/room.html` 라우트가 명시적으로 없다는 점에 유의 — 실패하면 별도 이슈로 분리한다.)
- [ ] B-1. room.html 초대 공유
  - 절차: 브라우저에서 `http://127.0.0.1:8643/room.html` 접속 → 방 생성(자동) → 닉네임 입장 → "카카오톡으로 초대하기" 클릭 → 공유 팝업에서 실제 전송.
  - 확인 방법: §1-0a~c + 실제 카톡 수신 여부.
  - 기대 결과: **미정 — 이게 이번 검증의 핵심 분기점.**
    - 성공하면: `file://` 가설 확정 + 로컬도 이미 허용됨. A의 4019는 착시 버그로 결론.
    - 4019가 나면: 로컬 오리진(`127.0.0.1:8643`)이 콘솔에 미등록된 것이 원인인 것으로 추정 → §4 체크리스트로 가서 `http://127.0.0.1:8643` 등록 여부를 확인하고, 필요시 등록 후 재측정. (`localhost:8643`과 `127.0.0.1:8643`은 카카오 판정상 **서로 다른 호스트**이므로 주소창에 쓴 그대로 등록됐는지 볼 것.)
- [ ] B-2. index.html 회귀 (대조군)
  - 절차: 같은 로컬 서버에서 `http://127.0.0.1:8643/` → 파이프라인을 `DONE`까지 진행(또는 기존 검증 방식) → 공유 버튼 클릭.
  - 확인 방법: B-1과 동일한 콘솔/Network/수신 확인.
  - 기대 결과: B-1과 **같은 결과**여야 정상(둘 다 성공 or 둘 다 4019). 만약 index만 되고 room만 안 되면 §2의 차이점 문제이므로 B-1 로그 전문을 보관할 것.

### 시나리오 C. OCI 배포본 경유 (http://144.24.91.250.sslip.io:8643)

- [ ] C-0. 배포본 살아있음 확인
  - 절차: `curl -i http://144.24.91.250.sslip.io:8643/health` + `curl -i http://144.24.91.250.sslip.io:8643/room.html`.
  - 확인 방법: 둘 다 200인지.
  - 기대 결과: 200. 실패하면 카카오 검증 이전에 배포/보안리스트(TCP 8643) 문제로 분리한다.
- [ ] C-1. room.html 초대 공유 (메인 판정)
  - 절차: `http://144.24.91.250.sslip.io:8643/room.html` 접속 → 입장 → "카카오톡으로 초대하기" → 실제 전송.
  - 확인 방법: §1-0a~c + 실제 카톡 수신 + 수신된 링크 클릭 시 `?room=<id>` 방으로 입장되는지.
  - 기대 결과: **성공이 정상.** 도메인 등록은 도메인 단위이지 페이지 단위가 아니므로(추정 아님 — 공식 등록 규칙상 경로 제외), index.html이 되던 도메인에서 room.html도 되어야 한다. 실패(4019)하면 §4로 가서 등록값 오타·포트 누락·http/https 착오를 확인한다.

## 2. room.html이 index.html과 달라서 생길 수 있는 추가 문제 점검

> 이론상 도메인 검증은 "도메인 단위"이므로 페이지가 달라도 되어야 하지만, 아래 4가지는 실제로 확인할 것.

- [ ] 2-1. 공유 링크에 `?room=<id>` 쿼리가 붙는 점
  - 점검: `room.html:249-264`는 `location.href` + `?room=${roomId}`를 `webUrl`/`mobileWebUrl`로 공유. 카카오 도메인 판정은 **도메인만 보고 경로·쿼리는 제외**하는 것이 공식 규칙이므로, 쿼리 유무 자체는 4019 원인이 아닌 것으로 판단 (추정 아님 — "입력한 도메인에 포함한 경로는 제외됨" 규칙 인용).
  - 확인 방법: C-1 성공 시 수신 메시지의 링크가 `.../room.html?room=<id>` 그대로인지 + 클릭 시 해당 방 입장이 되는지.
  - 기대 결과: 링크·입장 모두 정상. 단, **공유되는 링크의 도메인**이 제품 링크 관리에 등록된 도메인과 일치해야 한다는 별도 규칙이 있으므로(데브톡: "공유하기에 사용된 링크는 제품 링크 관리에 등록된 도메인만 사용 가능"), `room.html`이 `file://`·`localhost`·`127.0.0.1` 등 미등록 오리진에서 만든 URL을 공유하면 받는 쪽 링크가 기본 도메인으로 바뀌거나 실패할 수 있다 (추정: 버전별 동작 상이 가능) → B/C에서는 주소창 오리진과 공유 URL 오리진이 같은지 항상 함께 기록할 것.
- [ ] 2-2. 버튼이 "항상 노출" vs "DONE 시 동적 생성"
  - 점검: index는 파이프라인 `DONE`/`design_url` 시점에 버튼을 동적으로 붙이지만(`index.html:104-110`), room은 `#shareBtn`이 상시 노출(`room.html:123`). 자동화 클릭 오탐(`Cannot read properties of null (reading 'focus')`, `c510f2b` 기록)과는 무관하게 **사람이 직접 클릭**하는 조건으로만 비교할 것.
  - 확인 방법: 모든 시나리오에서 Playwright/자동화 클릭 금지, 실제 마우스·터치 클릭으로만 판정.
  - 기대 결과: 수동 클릭 조건에서 두 페이지 동작이 일치해야 정상.
- [ ] 2-3. SDK 초기화 가드 차이

## 5. 향후 재발 방지책 ("file://로 열어서 생긴 착시 버그"를 다시 안 겪기)

> 아래는 제안이며, 코드 수정은 이 문서의 범위가 아니다. 채택된 것만 별도 작업으로 실행한다.

- [ ] 5-1. 문서에 "반드시 서버 URL로 접속" 명시 (비용 5분, 효과 큼 — 우선 권장)
  - 내용: `README` 또는 `STATUS.md` (또는 두 곳 다) 상단에 한 줄 추가: "`static/*.html`은 더블클릭(`file://`)으로 열지 말고 반드시 `http://127.0.0.1:8643/room.html` (로컬) 또는 `http://144.24.91.250.sslip.io:8643/room.html` (배포본)로 접속한다. `file://`에서는 방 API와 카카오 공유가 모두 실패한다."
  - 확인할 것: 문구 추가 후 신규 참여자가 `file://`로 여는 실수가 없어지는지.
- [ ] 5-2. 로컬 개발 절차 고정 (STATUS/LOCAL_SETUP에 3줄 절차)
  - 내용: `docker compose up --build` → `curl -i http://127.0.0.1:8643/health` → 브라우저는 주소창에 `http://127.0.0.1:8643/room.html` 입력. 북마크 권장.
  - 확인할 것: `localhost`와 `127.0.0.1`을 혼용하지 않고 한쪽으로 통일했는지 (카카오 판정상 별개 호스트이므로).
- [ ] 5-3. `file://` 접근 시 조기 경고 (코드 변경 필요 — 이번 작업 범위 밖, 제안만)
  - 안: `room.html`·`index.html` 선두 스크립트에 `if (location.protocol === 'file:')` 경고를 넣는(배너 또는 `alert`) 안이 있다. 단, 구현·문구·적용 파일은 별도 결정이 필요하므로 여기서는 채택하지 않고 후보로만 기록한다.
- [ ] 5-4. 검증 규칙화 ("카카오 손댔으면 §1 매트릭스 1행")
  - 내용: 카카오 공유 관련 변경이 있으면 커밋 메시지에 `A(file://)=4019 정상 / B(로컬) / C(OCI)` 3행 결과를 붙이는 규칙. `PM_NEXT_STRATEGY.md`에 지적된 "문서와 실물 어긋남" 재발도 막는다.
  - 확인할 것: 다음 카카오 변경 커밋부터 매트릭스 첨부 여부.
- [ ] 5-5. 콘솔 등록값 스냅샷 보관 (민감정보 제외)
  - 내용: §4 확인 뒤 등록된 도메인 문자열(공개 정보)만 `ENVIRONMENT.md` §3-6에 추가로 적고 날짜를 남긴다. 키·시크릿은 절대 기록하지 않는다.
  - 확인할 것: 다음 4019 발생 시 "등록값이 바뀐 것인지, 사용법이 잘못된 것인지"를 1분 안에 구분할 수 있어야 한다.
